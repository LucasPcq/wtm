# next/ — wtm as use-case slices

`wtm-next` (`make next` → `bin/wtm-next`) is wtm rebuilt as plain functions: a pure domain, one package per use case behind an in-process API, adapters behind the small interfaces each use case declares, a command line per command over a shared presentation kit, and a local web server over the same API (`wtm-next ui`). It works on the same repositories and state files as `wtm`: same state directory, `meta.json`, `config.toml` keys, operation locks and `repos.json`; its daemon is its own (`wtm-next daemon`: wtm's daemon, which holds the jobs of the machine, and the event bus, schema v2), on the socket, lock and index of jobs legacy's daemon uses, so each takes over the jobs the other left. Nothing here imports `github.com/LucasPcq/wtm/internal/…`.

## Layout

```

  ui/                  the presentation kit every command's cli shares, knowing no command
    cli/               the root: version, --quiet, help, signals, the exit code a command's failure sets
    output/            the streams (stdin, stdout, stderr, whether each is a terminal, a colour renderer each), frames and blocks, progress (one subject at a time, or several at once, a row per subject or per job: `Concurrent`), failures, plans, the hook view, the v2 envelope writer
    form/              a command's form, generic over its schema: form.Command (its flags, its request, its launch, the conclusion of its run, its command line), form.Query (the same for a read, with its subject asked first, and again among what it matches once refused as ambiguous, its picker, the machine formats it prints besides json, tree's mermaid, and the bare text of a read a shell captures, resolve's path), form.Stream (a stream's flags and request), the session and a step per field kind, the wizard that walks them to a recap and applies, or to the last step of a read's picker
    widget/            the inputs a step asks with: select list, multi-select, text field, text list, their styles, and the problem an input shows with the steps that get past it
    runview/           the live view of the jobs of some worktrees (`runview.Run`): their list, the shared services first, the terminal of the job selected attached through wtm's daemon, a band of notices; over its own port, `runview.Daemon` (`Jobs`, `Attach`, `Resize`, `Lines`), which `adapter/daemon.Daemon` satisfies
    formtest/          for a command's tests: the driver that plays its wizard key by key, golden files, the v2 envelope decoded, a run of its command line (`Run`, `Printed`), a terminal that keeps pressing enter (`Enters`), a use case whose previews and applies a test scripts (`Previewing`)
  api/                 the catalogue of the commands and its streams (`api.Stream`, a command that sends lines until stopped), knowing none of them: each one's name, its schema (domain.Form), the Go types of its plan and its detail, its questions as the repository stands and its execution, the answers by field in and a domain.Envelope out, for a surface other than the command line, which maps the kind of its error onto a status of its own; and the schema it publishes (`api.v2.schema.json`, `api.Schema()`)
  daemon/              wtm's daemon: the jobs of the machine started, watched and stopped as its clients ask, recorded in its index and taken over from the daemon before (an orphan reaped, a service crashed, a detached stack and a claim kept), its job events published on the bus, each job's output kept (its last lines, its log, its raw terminal for a client attached), the names of its services served by its proxy; blind to git, it reaches the world through its `port.go` (`Spawn`, `Process`, `Orphans`, `Index`, `OpenLog`, `ReadLog`, `Publish`, `Exists`, `Routes`, `Probe`)
  web/                 the local HTTP server over the catalogue (`wtm-next ui`): the routes of each repository wtm knows, the guard of every request, an operation's progress and the event stream as server-sent events, the status of each kind of error, the page (the front's build in `dist/`, embedded; `noui/` in a binary built `-tags noui`); what it cannot reach (the repositories, the token, the kill, a follow-up's command line, the schema) it is given by `cmd/wtm-next` in `web.Params`
web/                   the web front (React, Vite, shadcn/ui), no Go file: `make ui` builds it into internal/web/dist (docs/dev/web-front.md)
```
No file format lives in `domain/`: `adapter/config` owns the shapes of `config.toml` and `run.toml` (every key, strict decode) and maps them onto `domain/project`. `worktree.Meta` keeps its JSON tags, because `meta.json` is the record itself, shared with `wtm`; `worktree.Identity` keeps those of the events payload.

A use case reads in one place. `command/<name>/usecase.go` tells the whole request top to bottom in `Run`: begin the operation (`service/operation`), plan under its locks, fingerprint, stop on a dry run, refuse a stale plan, apply between the started and finished events; then `Plan` (observe what the repository holds, settle the request on it, decide), `Apply` and `Questions` when it asks. `rules.go` holds what it observes and decides from, pure; `questions.go` its form, the schema of its fields (paths, answers, options and the facts of each, origins, skips) and validation, with no word: the CLI words each field in `cli/words.go`, the web in its screen's `words.ts`; `port.go` the interfaces it reaches the world through. The root of a command holds these four files, their tests and `cli/`, nothing else (archlint, rule `slicefiles`). A service is concrete and called directly; a port is an interface, for the outside world only. A package is split only when it passes about 1,000 lines and a seam is natural.

## The published schema

`internal/api/api.v2.schema.json` is the JSON Schema of everything the catalogue sends a surface: the v2 envelope, the form and its fields, the events (a `$ref` to `adapter/events/events.v2.json`), each command's request, plan, detail and envelope, each stream's request and envelope, and what the web server's own routes answer and read (`web.*`, written beside the server in `internal/web/web.schema.json`). It is generated from the Go types, never edited by hand: `make schema` rewrites it, `make test-next` fails while it is stale and validates against it each `catalogue_*` golden of `cmd/wtm-next` and each `envelope_*` golden of a command's `cli`, and the web server's real responses. `api.Schema()` returns it for a server; the site publishes it, with `events.v2.json`, on `wtm.sh/schemas/`. How it is built: `.claude/skills/go-architecture/references/contract.md`, "The published schema".

## Import rules

`make lint` checks them (`tools/archlint`, rule `next`).

| Package | May import |
| -- | -- |
| `domain`, `domain/*` | stdlib, `domain/*` |
| `service/<name>` | `domain/*`, stdlib — never another service, `command/*`, `adapter/*`, `ui/*` |
| `command/<name>` | `domain/*`, `service/*`, stdlib — never another command, its own `cli`, `adapter/*`, `ui/*` |
| `service/<name>test` | what `service/<name>` may, third party, and `service/<name>`; imported from a `_test.go` only |
| `command/<name>/cli` | `command/<name>`, `domain/*`, `ui/*`, stdlib, third party — never another command nor its `cli`, `service/*`, `adapter/*` |
| `adapter/<name>` | `domain/*`, `adapter/statefile`, `adapter/shell` (the one way to start a child), stdlib, third party — never `service/*`, `command/*`, `ui/*`, another adapter |
| `adapter/<name>test` | what `adapter/<name>` may, and `adapter/<name>`; imported from a `_test.go` only |
| `ui/<name>` | `domain/*`, `ui/*`, stdlib, third party — never `command/*`, `service/*`, `adapter/*` |
| `ui/<name>test` | what `ui/<name>` may, `ui/<name>` included; imported from a `_test.go` only |
| `api` | `domain/*`, stdlib — never `command/*`, `service/*`, `adapter/*`, `ui/*`, third party |
| `web` | `api`, `domain/*`, stdlib — never `command/*`, `service/*`, `adapter/*`, `ui/*`, third party |
| `daemon` | `domain/*`, stdlib — never `command/*`, `service/*`, `adapter/*`, `ui/*`, `api`, `web`, third party: blind to git |
| any test | never `github.com/LucasPcq/wtm/internal/…`; it sits beside the package it tests, never in a directory of tests alone |
| `cmd/wtm-next` | anything under `next/` except a fake |

A package in no row is refused: the root of `next/`, a second `cmd/<name>`, anything outside these directories. A name ending in `test` under `service/`, `adapter/` or `ui/` is reserved for the kit of the package beside it: `service/latest`, with no `service/la`, is refused. A service is one package: a sub-package `service/<name>/<sub>` falls in the `service/<name>` row and may not import `service/<name>`; a command's `cli` likewise imports no sub-package of its own.

A code a command declares starts with its `Name` and a dot (`create.path_exists`); a code several commands share is a `domain` constant (archlint, rule `codeprefix`).

Only the edges read the environment: `ui/cli` once (`ReadEnv`), `ui/output` the terminal, `cmd/wtm-next` `$WTM_STATE_DIR`, an adapter what its own tool needs; never a domain package, a service or a command, which take the value as an input (archlint, rule `envread`).

A use case or a service declares the ports it needs in its `port.go`, interface types and function types only (archlint, rule `portfile`); an adapter exports a concrete type that satisfies them, checked by the compiler in `cmd/wtm-next`.

## Reading a command

`wtm-next create feat/x --from main`, hop by hop:

1. `cmd/wtm-next/main.go → main`: `ui/output.System()` reads the process's streams and `ui/cli.ReadEnv()` its environment once (the working directory, `$WTM_PROJECT_DIR`, `$WTM_CORRELATION_ID`), and `ui/cli.Main` runs the root with `command/create/cli.New(streams, env, openCreate, commandLine)` registered on it; `ui/cli/root.go → Execute` maps the failure a command returns onto its exit code.
2. `command/create/cli/command.go → createCommand.run` hands the command line to `ui/form/command.go → Command.Launch`: `uicli.Run.Begin` refuses an invalid correlation ID before any repository is looked up, the flags, registered from create's schema, become a `create.Request`, `openCreate(ctx, env.ProjectDir)` (`cmd/wtm-next/project.go`) finds the repository of that directory, always from its main worktree, and wires the use case (`cmd/wtm-next/wire.go → wire`), then it runs the wizard when the user can see and answer it (stdin and stderr terminals, `TERM` not `dumb`, human output, no `--yes` nor `--expect-fingerprint`: `output.Streams.CanPrompt`, `Command.Ask`), else `create.UseCase.Run` with its `domain.RunOptions`, the correlation ID among them; `Launch` hands the run to `Command.Conclude`.
3. `command/create/usecase.go → UseCase.Run`: `operation.Service.Begin` records the operation with the options' correlation ID, refusing an invalid one, and takes its locks (`service/operation/operation.go`), `operation.PlanUnderLocks` plans under them, `operation.Fingerprint` fingerprints the plan, a dry run stops there, `Op.Expect` refuses a stale plan, then `Apply` runs between the started and finished events.
4. `command/create/usecase.go → UseCase.Plan`: `Observe` reads the repository (`repository.Service.Observe`: config, snapshot, run.toml) and what create reads itself through the ports of `port.go`, `Resolve` (`questions.go`) settles the request on those facts, `Decide` (`rules.go`) turns them into the plan.
5. `command/create/usecase.go → UseCase.Apply`: an optional fast-forward of the source (`provision.Service.FastForwardEach`, `service/provision/fastforward.go`, each source it could not move a warning under create's code), then `provision.Service.Run` (`service/provision/provision.go`) per branch, with `provision.ParamsOf`: the worktree, its env, its meta record, its hooks; `provision.Service.Remember` then writes the answers asked to be remembered.
6. `adapter/git/worktree.go → Repo.AddWorktree`: the port's implementation runs `git worktree add`.
7. Back in `ui/form/command.go → Command.Conclude`: a refusal, or the dry run drawn from create's `Preview` (`form.PreviewOf`) and ended on the line that applies exactly that plan, or the outcome create's `Draw` draws (`command/create/cli/output.go → drawOutcome`, a call to `ui/output.DrawApplied`); with `--output json`, `create.Outcome.Envelope` (`domain.Outcome.Envelope`) reports the run as a `domain.Envelope`, which `ui/output.Envelope` writes with each field spelled as its flag.

A second command is its own `command/<name>/` (use case, ports, rules, questions, `cli/`) and one line in each list of `cmd/wtm-next`: its constructor in `main.go`'s `commands`, its opener in `project.go` (`opener(func(a app) <name>.UseCase { return a.<Name> })`), its binding in `catalogue.go` (`api.Bind(<name>.Name, open, UseCase.Questions, UseCase.Run)`), its adapters wired in `wire.go`. `registration_test.go` fails when a command of `main.go` is missing from the catalogue or from the wiring, and `contract_test.go` when it is not in the catalogue contract (`.claude/skills/go-architecture/references/contract.md`, "The catalogue contract").

A read, `command/list`, `command/resolve`, `command/status`, `command/tree`, `command/runlogs`, `command/runps` or `command/runlist`, walks the same hops with a `form.Query` in place of a `form.Command`, under the contract of a read (`.claude/skills/go-architecture/references/contract.md`, "A read"). `resolve`'s query is `Captured`: what it draws is the path alone on stdout, which `go`, the shell function `wtm shell-init` installs, reads and enters; a follow-up that enters a worktree names `go` with the answers of resolve (`domain.Enter`), and `commandLine` spells it `wtm go <worktree>`.

A stream, `command/events`, never ends on its own: its use case is built once in `wire.go` (`eventStream`), not per repository in `app`, since it may follow every repository; its cli is a `form.Stream` (flags and `--output` only) that prints each line itself; `catalogue.go` lists it in `streams()` (`api.BindStream`) rather than the catalogue, and `registration_test.go` names it in `streamsListed` (`.claude/skills/go-architecture/references/contract.md`, "A stream"). Every opener of `project.go` registers the repository it opens through `service/registry` (`knownRepos` in `wire.go`: `repos.json`, the bus, and "initialized" read by `config.Project.Initialized` in the state directory `stateDir` locates; `movedState`, the one reader of `$WTM_STATE_DIR`, says when the registry is left alone), for a stream of every repository; the stream registers the one it watches after reading its config, never one it joins. `openEvents` opens a repository with the same pieces `wire` builds (`wireParams.facts`, `wireParams.repo`). Its request reads where its caller stands (`domain.Caller`): the form engine sets it from the command line's environment and `api.BindStream` from the call's directory, so a relative `--repo` is read from the same place on both, and a call naming no directory stands nowhere and streams every repository.

A follow-up another command gives that names a migrated command is spelled from that command's schema: `commandLine` (`cmd/wtm-next/wire.go`, handed to each command's `cli.New`) hands it to the command's `cli.Line` (clean's, prune's, fast-forward's, sync's, exec's, reparent's and run up's over `form.Command.Spell`, run logs' over `form.Query.Spell`), and spells the others as the legacy `wtm` runs them; `registration_test.go` fails on a follow-up naming a migrated command `commandLine` does not hand on, or whose answers its request refuses.

Todo: the follow-up a read's picker ends on is printed by `form.Query`; once every command it names has migrated, it runs in this process instead (`api.Catalogue.Find(followUp.Command)` with its answers).

## A worktree named, a worktree the command chose

A worktree the user names (an argument, a web answer, a pick changed in the wizard) and one the command chose itself are kept apart by the request: its `worktree` answers name the first; no `worktree` answer leaves the choice to the command (the wizard's default pick confirmed untouched answers none, as an unattended run naming none does; fast-forward's `--all` asks for it explicitly). A worktree a safety check refuses (prune: locked, dirty, unpushed, an open pull request, jobs up; fast-forward: behind origin with uncommitted changes; sync: uncommitted changes in a worktree it would rebase) refuses the whole request when named: a `refused` error (`<command>.unsafe`, exit 23) with one problem per blocker on its entry and the request forced as its follow-up (`<command>.force`). When the command chose it, it is left as it is: a plan entry with its blockers and no phase, an item `skipped` with the reason `ruled_out`, one warning per worktree (`prune.kept`, `fast-forward.kept`, `sync.kept`, its `worktree` and `blockers`), the last followed by one request naming every worktree left forced, and the others go on. The default pick leaves such a worktree out, so the pick and the plan agree. The wizard's step for the worktrees answers no worktree when its default pick is confirmed untouched (`ui/form`'s `MultiSelectStep.Chosen`, which prune's, fast-forward's and sync's `cli/steps.go` set). Sync's descendants of a worktree named are the command's choice too: one with uncommitted changes is kept, never refused.

A command that reads origin (prune for `--gone`, fast-forward, sync) fetches it once per plan, unless the request answers the flag-only `no_fetch` (`--no-fetch`): it then reads origin as last fetched. A surface that plans again on the person's choices, as the web's dialogs do on each tick and each apply, sends it, so a flow fetches once, with its first dry run; the follow-up a plan offers (the request forced) never carries it.

## What sync rebases

`sync` rebases worktrees onto their parent, the branch each meta record names, down the stack (`worktree.Stack.Cascade`): each worktree named and, unless `descendants` is answered no (`--descendants=false`), every worktree under it, parents before children; with none named, those that need a sync (`NeedsSync`); `--all`, every worktree but the main one and the base branch's, which it never rebases (naming one is refused, followed by `fast-forward`). One fetch of origin first. Then, in `Apply`: the branches rebased onto but not rebased, the base among them (`Plan.Onto`), are fast-forwarded to origin's planned commit unless `ff_parents` is answered no (`provision.Service.FastForward` in its worktree, a worktree with uncommitted changes kept; the ref moved to that commit, `UpdateBranch`, for a branch no worktree holds), each an item of the outcome before the worktrees': done with the commits it took (`Detail.Commits`, no `parent`), skipped with `sync.ff_failed` when refused (its children rebased onto it as it stands: it never fails the run), or interrupted; then each worktree, between its unit events: its own origin's commits brought in when origin is only ahead (`fast_forward`), `git rebase --onto <parent> <fork point>` (`rebase`: onto the parent's commit as planned, or, for a parent rebased in this run, as it then stands; the fork point read from the parent's reflog before any branch moves, so a child replays its own commits alone even once its parent was rewritten, but the merge base instead when the fork point would skip a commit that has no rewritten counterpart on the parent, same author, author date and subject, as a commit the parent held then lost to a reset), then, with `push`, `git push --force-with-lease=<branch>:<origin's planned tip>` (`push`), never for a branch origin has never had. A rebase that stops on a conflict is aborted, the worktree as it was (`sync.conflict`, kind conflict, exit 24, its files in the params), or left in progress with `keep_conflict`; the worktrees under it are `skipped`/`blocked`. Its follow-ups resolve it (`--keep-conflict`), or, left in progress, enter it then sync what is left. The descendants a run left out (`--descendants=false`) get their own sync (`sync.left_out`). A worktree is left as it is, with a warning and what moves it on, when its directory is gone, git is in the middle of an operation in it, its record does not read, it records no parent or one that is gone, its parents lead back to it (a cycle refuses only the run that names one of its members, `sync.cycle`, exit 23), its parent is left by this run, or origin holds commits on its branch it never held (`NeverHeld`, read from the branch's reflog, so a branch rewritten since it was pushed is not diverged; a commit of origin pulled then dropped locally, by an interactive rebase, counts as held, and `--push` overwrites it), or it shares no commit with its parent (`unrelated`). A first Ctrl+C lets the git step under way finish and starts no other, the push included. The plan names each worktree there as a descendant (`descendant`), under a worktree named or under one its default pick picks, and the descendants left out (`left_out`); each row carries its parent and its depth in the stack; the picker's options carry the parent, the commits of it a worktree lacks (`behind`) and the operation under way. reparent's `reparent.sync`, status's `status.behind` and the menus' `sync` (`worktree.ActionSync`) follow up with it; fast-forward's `fast-forward.diverged` does not, since sync never rebases onto origin: it enters the worktree to reconcile it by hand.

## What env reconciles

`env` reconciles worktrees' `.env` files (`command/env`): those named; with none named, the one the caller stands in, its wizard offering the worktrees out of step checked beside it (`MultiSelectField.Prechecked`); `--all`, every worktree on a branch. For each, `env.Settle` (`domain/env/reconcile.go`) decides, the one place that decides it for `env` and `env show`: each declared file the worktree lacks is rebuilt from its scaffold (the template under the `example` strategy, else the source's copy); each key a source gives a value and the file lacks is added; a key holding another value than its source's is kept unless `--overwrite`, a key in no source unless `--prune`; then what wtm writes, `env.Resolve` (`domain/env/settle.go`), the one computation `run addressing` (LUC-347) calls too: the ports and addresses run.toml links moved onto the worktree's ordinal, the `[[env]]` values and `COMPOSE_PROJECT_NAME`. The keys wtm writes are never compared with a source, but under the verbatim isolation. The sources are the worktree's strategy (`--from` for one run): `example` the template (no value), `main` the main checkout's copy, `parent` the parent worktree's, the main checkout's when it has none. Nothing is written for a worktree whose run.toml does not read (`env.ports_not_settled`) or that has yet to choose its isolation (`env.isolation_pending`, followed by `env <wt> --isolation isolated`): its keys only. A worktree with no ordinal is numbered by the apply, which settles its ports then. The main checkout keeps its addresses spelled with ports when its `.env` spells them so. `--isolation isolated|verbatim` switches the worktrees asked, only those yet to choose theirs when some are, the main checkout refused (`env.main_isolated`): verbatim puts the values wtm wrote back to the source's, else the main checkout's; the isolation is recorded in meta.json once the files are in line. The fingerprint covers each file as it stands, so a file edited since the preview refuses the apply. A worktree whose files cannot be read is left, said why (`env.unreadable`), and records nothing. A port wtm finds nothing to move in is left alone and said (`env.env_ports_left_alone`, with its ports). A job up in a worktree whose `.env` in its directory changed is warned (`env.restart`) with `run start <job> --restart`. Every value wtm does not write is withheld unless `--show-values`.

`env show` (`command/envshow`) reads one worktree's files from the same `env.Settle`: apps (a directory holding a declared file, the jobs whose `cwd` it is), files (where each comes from: `template`, `main`, `parent`, `fallback`, `own` for the main checkout, `none`), keys (what each follows, `port`, `address`, `value`, `owned`, `nothing`, `copied`; its value in main and here, what wtm writes, whether it is out of step), and the keys to check (`unlinked`: a key no link follows whose value holds a declared port, alone or in an address of this machine, or such an address, `env.LooksLinked`; `out_of_step`; `left_alone`, a linked key wtm finds nothing to move in, with why). A key wtm writes stands against what it writes, never against a source, as `env` reconciles it; the credentials of a URL it shows unasked are masked (`env.WithoutCredentials`).

## What checkout reads of GitHub

`checkout` is create for one branch whose name, parent and facts come from a pull request. It asks GitHub through `adapter/github`, the one GitHub port: `PullRequest` (`gh pr view <n> --json …`) for the pull request asked, whatever its state, and `OpenPullRequests` (`gh pr list --state open --limit 50`, `--author @me` with `--mine`, `--search review-requested:@me` with `--review`, the two refused together) for the picker, which only `Questions` reads. Without gh, signed out, or in a repository GitHub does not hold, it is refused `checkout.github_unavailable` (precondition, exit 25), its message saying what to do and its `reason` param naming which (`worktree.UnavailableParams`, the one helper every GitHub-unavailable fact goes through: checkout's refusal and every `<command>.prs_unavailable` warning, of the reads and of clean and prune), for the three a person fixes outside wtm (`worktree.ReasonGHMissing`, `ReasonSignedOut` when `gh auth status` names `gh auth login` as its fix, `ReasonNotOnGitHub`: `worktree.ErrGitHubCLIMissing`, `ErrGitHubSignedOut`, `ErrNotOnGitHub`, each an `ErrPullRequestsUnavailable`), absent for any other failure of gh; a number GitHub has no pull request of is a `not_found` problem of `pr` (exit 2). Before it reads the repository, it fetches the pull request's branch from origin (`FetchRef`) and reads the snapshot again, so the fast-forward is asked from where origin stands now, unless `--no-fetch` reads it as last fetched, a stale remote-tracking branch included (the web sends it on its form's later asks only, once an ask fetched that pull request's branch without a refusal; its dry run and its run fetch); a fetch that fails is the warning `checkout.fetch_failed`, the plan standing on origin as last fetched, but for a branch origin no longer has (`worktree.ErrNoRemoteBranch`, a merged pull request's auto-deleted branch fetched before without `--prune`): its remote-tracking branch is set aside, as no branch to track nor to stand against. The branch is placed by `worktree.Place`: checked out as it is when it exists locally (`check_out`), else tracking origin's (`resume`); one neither has is refused `checkout.head_missing`, a fork's `checkout.fork` (with `gh pr checkout <n>` in its message), one a worktree holds `checkout.checked_out_elsewhere` with the `go` that jumps in. Its parent is the branch the pull request merges into, `origin/<base>` when only origin has it, never the pull request's own branch (`self_parent`), and `--from` is required when neither holds it. A pull request merged or closed is checked out with the warning `checkout.pr_not_open`. The request locks the repository alone, since the branch is not known before the pull request is read: the plan, which names the branch, is made again once its lock is held. `cmd/wtm-next` asks GitHub and fetches each branch once per opened command (`askedOnce`, as prune's `fetchedOnce`), since the wizard asks again at each of its steps. Each option of the picker carries its pull request (`pull_request`), where its branch stands against origin when it exists locally (`origin`: state, ahead, behind; fetched for the pull request asked), and one that cannot be checked out its tag and the problem picking it raises (`problem`: a fork's names `gh pr checkout <n>` in its `command` param, one a worktree holds names that worktree's `path` and the `go` that jumps in); the pull request asked by its number is among the options even when it is no longer open, and the parent it defaults to says so (`origin: pull_request`). The plan carries the pull request (`pull_request`); its fingerprint covers only its number, branch, head commit, base and state, so a push to it between the preview and the apply is a stale plan and an edit of its title is not; a select step does not check its field's problems, so a pull request the picker tags `fork` or `checked_out` is refused at the wizard's recap.

## What reparent changes

`reparent` rewrites one field of a worktree's meta record, `source_branch`, through `repository.Reparent`: no git ref, file of the worktree nor process moves, so whatever state a worktree is in, nothing is lost and there is no `--force`; the next `sync` rebases onto the new parent. A worktree can move when wtm recorded it, it is on a branch and it is neither the main worktree nor the base branch's; one whose record exists but does not read is refused with that cause (`reparent.meta_unreadable`), one whose record a newer wtm wrote with `reparent.meta_newer` (exit 22); with none named, the one the caller stands in moves. A new parent among the worktrees moved, or under one of them (`Stack.Within`, which follows every recorded parent), is refused as `self_parent` or `reparent.cycle` on `to`, and the select leaves both out of its options with that same field error in `Refused`. Its lock guards the move: each worktree moved exclusive, and the new parent and every branch it sits under shared, so neither another reparent closing a cycle nor a clean removing the parent can run beside it (`lock.held`, exit 24). A worktree already on the new parent is `done` / `unchanged`, nothing written. The outcome follows up with the `sync` of the worktrees moved and, per worktree, the reparent that moves it back (`reparent.undo`), offered while the parent it left is a branch it does not sit above. list's and tree's menus offer `reparent` (`worktree.ActionReparent`) on a worktree that can move, and say why on the others (`main_worktree`, `base_branch`, `no_branch`, `missing`, `unrecorded`, `meta_unreadable`); tree marks a worktree whose parent branch is gone (`parent_gone`), and status names it, or a worktree whose parents lead back to it, as a problem fixed by `reparent <it> --to <base>` (`status.parent_gone`, `status.cycle`).

## What clean and prune do with the run module

`clean` and `prune` remove a worktree with what it runs and the data it made in shared services, through `service/teardown`, in the legacy wtm's order. Jobs up never refuse a removal: each removal whose worktree runs jobs of its own (its claims on shared services are not) starts with a phase `stop_jobs`, each of them stopped through wtm's daemon (`stop`), then listed again; one still up, or a daemon that cannot tell (`run.ErrUnknown`, warned at plan time `clean.jobs_unknown`), fails the item, `clean.stop_failed`, unless forced, which removes it all the same with `clean.jobs_left`, followed by `run down` of the removed worktree's path. Then its `on_clean` hooks, the removal, and a phase `drop_data`: each namespace its record names (`namespaces`, job names) of a shared job declaring a `remove` is dropped, its `remove` run as a chain of one hook from the main checkout with the environment the worktree's jobs got (its job environment, read while it is there, and the job's ports), within 30 seconds; its job logs (`<state>/logs/<branch>`) are purged. Once every removal of the run is made, each worktree removed has its jobs and claims let go of (`stop_all`: the last claim stops a shared service, which then takes no namespace back), `clean.release_failed` when that fails.

The plan says per removal what becomes of its data (`data`: `job`, `name`, `status`, `reason`): `drop`, its service up in this repository's main checkout (a job of the same name in another repository is not it); `defer`, its service down; `keep`, for `--keep-data` (`reason: keep_data`) or another worktree that reaches the namespace under the same name (`shared_name`; the main checkout as a start there names it, on a branch or not); `start`, `--drop-data` (the field `drop_data`, the wizard's Data step, asked only when a service holding data is down, `defer` unattended): the service is started in the main checkout before the first removal, the data dropped, the service stopped again after the last. `--keep-data` and `--drop-data` together are refused, `clean.data_both_ways`. The outcome's detail names each namespace with what became of it (`namespaces`: `dropped`, `deferred`, `kept`, `failed`), each that stays warned (`clean.data_deferred`, `clean.data_kept`, `clean.drop_failed`); prune the same with `prune.*`.

A namespace that could not be dropped is owed in `pending-removals.toml`, beside the records in the project's state directory, the legacy wtm's file (`adapter/store.Owed`): `[[pending]] job, worktree, ordinal`, its legacy keys, and the namespace's `name` and the `env` its drop runs with, so a drop paid later runs as it would have run at once; a file with an entry keeping them is written `schema = 2`, which the legacy wtm reads (ignoring the new keys) and refuses to rewrite; an entry it wrote is paid from its slug and ordinal. A queue that cannot be read owes nothing; it is removed once nothing is owed. The drops owed are paid by `prune`, first, and by `run up`, once its jobs are started, each planning them: the plan's `owed` (`job`, `name`, `worktree`, a recap row `Owed`) lists each drop owed whose service is up in the main checkout, or, for `run up`, which it starts or joins; a plan with no worktree to prune that pays one is no empty plan. The others stay owed, `prune.owed` counting them per service. What became of each is an item of the outcome after the worktrees, its subject the namespace and its detail the debt (`owed`): `done` once dropped (unchanged when another run dropped it first), `failed` with the error it failed on (`<command>.drop_failed`, or `<command>.owed_unrecorded` when the queue could not give it up: not dropped), `skipped`, `not_reached`, when the run was cancelled first or its service is not up after all (a start that failed to bring it up); each surface draws the drops from these items, never from the plan, and counts them apart from the worktrees (`✓ run up: 1 done · 1 owed drop made`). A drop is taken out of the queue under its lock before it is made, so one another run paid meanwhile is not made twice; one that fails goes back, and a queue that cannot take it back says it lost, with the command to drop it by hand (`<command>.owed_lost`). A crash between taking a debt out and dropping it leaks that namespace, never dropped, and never loses data. A drop owed that a worktree reaches again under the same name, the main checkout's on no branch included, is withdrawn instead (`<command>.owed_withdrawn`: its data is that worktree's now). `prune --drop-data` pays before it starts the services down, so what is owed to a service it starts stays owed until the next run.

A commit is unpushed when no other branch nor remote holds it (clean's and prune's rule, `service/teardown`), among the branch's and those of the commit its worktree stands on, read from git's worktree list so a worktree whose directory is gone keeps them; a merged pull request whose head GitHub keeps is the branch's tip and that commit holds them all (asked of the forge for every branch removed; one it cannot answer counts them). `clean` decides what is unsafe once, under its locks, before the `on_clean` hooks run, and does not check again after them: hooks write files (logs, Compose state) that would refuse every removal, so a change the user makes in the worktree while its hooks run goes with it. A worktree named whose meta record a newer wtm wrote is refused before anything is removed, `--force` or not (`clean.meta_newer`, `prune.meta_newer`, exit 22): `Meta.Load` and `Meta.Delete` refuse such a record as `Meta.Update` does, and its teardown is that wtm's; one prune chose itself is left as it is with a `prune.meta_newer` warning, and the others go on.

## What run up starts

`run up` (`command/runup`, `run-up` in the catalogue, `wtm-next run up` on the command line, a subcommand of `run`) starts a profile of run.toml in worktrees: those named, else the one the caller stands in; `--profile`, else the profile run.toml marks default, else its only one (several and none default is a required field, `--profile`); a run.toml with no profile starts every job, one with none at all is refused `run-up.not_initialized` (precondition 25, followed by `run init`). Its plan lists, per worktree, each job in the profile's order with its `action` (`start`; `up`, a service already up, left as it is; `join`, a shared service a worktree other than the main one holds), its `step`, the tasks it `waits_for`, the ports it binds offset for the worktree and the namespace a shared service makes for it; a plan whose every job is up already is empty. A worktree whose ports derive from an ordinal it lacks is numbered first (`provision.Service.Number`, its meta record written when it has none). Refused before anything starts: a daemon of another build or the legacy one holding jobs (`run-up.daemon_skew`, precondition 25, followed by `daemon restart`), a port another worktree's job holds (`run-up.port_clash`, refused 23, followed by the same start with `--exclusive` when stopping the others lifts it and the start is in one worktree; a port a job outside this repository's worktrees holds names it and where it runs, with no such follow-up), a runner and the job it starts both running in one worktree once the start is done (`run-up.runner_conflict`, a pair the start makes), a job whose `touches` reach data its worktree does not own, a verbatim worktree's source's or a shared service's with no namespace (`run-up.unsafe`, 23, a `run-up.foreign_data` problem per job, followed by the request forced). When other worktrees run jobs, `exclusive` stops them first (`stop_all` per worktree): `--exclusive`, `--parallel` (which says no), else run.toml's `concurrency` (`configured`, set aside with `run-up.exclusive_ignored` for several worktrees), else asked, keeping them by default; no answer of it is remembered, since `[wizard.remembered]` holds only the ids the legacy wtm reads. The worktrees start at once, each one's jobs in order, each between the phase events of `job` (`phase.started`/`phase.finished` naming the `job`, `phase.output` its lines): a task runs to its end and its failure stops its worktree (`run-up.job_failed`, the job's last lines and log in its detail), a service is launched, a start the daemon refuses as already running is `already_running`, a shared one is `joined` and its namespace recorded in the worktree's meta record (job names, as the legacy wtm). Each job's environment is the worktree's job environment and its own ports; a shared service's start names the main checkout (`run.Shared`) whichever worktree asks. Then the ports of the services started are dialled, on 127.0.0.1 then ::1, until they answer or `port_probe_timeout` (15 s, below 0 or `--no-probe` none; a job with `probe = false` or `binds_no_port` is not dialled; a port that never answers is `run-up.port_silent`), at least a second after the last launch has passed, and a service the daemon lists crashed since fails its worktree (`run-up.crashed`); a crash after that is the live view's and the events' to show. A first Ctrl+C leaves what the daemon took running (a start cut short is what the daemon now lists of it, when that changed since the plan: `started` or `joined` up, a task ended `done` or `failed` by its exit code, a service ended `crashed`; else `not_started`) and starts nothing more, the port check cut short saying nothing of the ports (exit 19). A worktree numbered by the start has its ports and namespaces from its new ordinal, in its detail and in the outcome's plan. The outcome is an item per worktree with each job's status (`started`, `already_running`, `joined`, `done`, `failed`, `crashed`, `not_started`), URL, log and ports (the command line draws the URLs as an `Addresses` block under the recap), then the start again where it did not pass (`run-up.retry`, its worktrees and its profile); `run logs` and `run down` of each worktree left with jobs up (`run-up.logs`, `run-up.down`). Every job records the `profile` it was started under, which the daemon lists. At a terminal, a start that left a job up opens the live view once every job is started (`ui/runview`, below); `-d`, `--quiet`, `--output json`, a dry run, a start that left nothing up and no terminal end on the outcome. Its worktree options say what each runs for itself (`up`, `crashed`, its claims and the shared services aside) and the shared services it holds (`holds`: its claims, and in the main checkout those it holds itself, never one it runs for the others alone); its profile options say which of the worktrees picked run them already (`running_in`). `list`'s detail names the jobs the daemon holds in each worktree (`jobs`: `name`, `kind`, `state`, none for a claim, `hold`, `profile`, `url`, the `exit_code` of a crash, `started_at`; null when the daemon cannot tell) and the profile its own jobs were started under (`profile`), which the Worktrees page shows; the web starts a profile from the Running page, a worktree's menu and its detail.

## What run logs reads

`run logs` (`command/runlogs`, `run-logs` in the catalogue, `wtm-next run logs` on the command line, a subcommand of `run`) is a read: what the jobs of worktrees printed. Its worktrees: those named (exact branches, or paths on no branch); none named at a terminal asks them (a multi-select, the one the caller stands in picked, each option with the logs it holds: its own jobs, a shared service the main checkout runs among main's, a claim none of its own; `--yes` skips it), anywhere else the one the caller stands in, refused naming the argument outside any. `--job` reads one job alone, one run.toml declares or the daemon lists in a worktree asked (any other is `run-logs.job_unknown`, 2); a run.toml absent is `run-logs.not_initialized` (25, followed by `run init`). Per worktree, the jobs in run.toml's order then the others the daemon lists there: the one named, else each the daemon lists there or that left a log; a shared service only in the main checkout or a worktree holding it, its lines and state the service's in the main checkout (`shared_in`). Each job's last lines (`run.MaxTail`, 1000) come from its log (`adapter/joblog.Tail`, behind the port `ReadLog`; the daemon's `lines` only for a job that keeps none; a log that exists and cannot be read is `run-logs.log_unreadable` on its worktree, the job listed all the same), so a daemon down, of another build or the legacy one changes nothing of them; the daemon is never started. The detail per worktree: its `path`, its `jobs`, each `name`, `kind`, `state` (`running`, `starting`, `crashed`, `exited`, `stopped`, the daemon's; `stopped` for a job only its log knows, `not_started` for one named that never ran), `hold`, `shared_in`, `exit_code`, `url`, `profile`, `log` (the file) and `lines` (`at`, `text`, the log's stamp out of the text). Warnings: `run-logs.jobs_unknown`, `run-logs.daemon_skew` (followed by `daemon restart`).

`UseCase.Watch` streams the same jobs as lines (`worktree`, `job`, `at`, `text`, and `mark` on the daemon's run mark): each job's last lines one job after the other, each worktree where no job ran and job named that never ran as an `Absent`, then, with `follow`, each new line of each job a process of this protocol's daemon runs, through `lines` with `follow`, until every one ended or its caller stops it (nil once the request is settled). A follower the daemon let go as it fell behind (`daemon.follower_behind`) follows again, the lines it sent already dropped (`Resume`: those older than the last one sent, and as many of its millisecond as were sent), a gap warned `run-logs.lines_dropped` when the last one sent is not where it should be; a follow the daemon refuses before a line reads the log instead, one it breaks off later is `run-logs.follow_broken`.

Its command line: at a terminal (stdin, stdout and stderr terminals, human output, no `--quiet`), the read, then the live view on its worktrees with the jobs read and `--job` selected (a job only its log knows listed `stopped`, its pane the read's lines); a read where no job ran opens none and says `= feat/c: no job has run`. `--search` (`--regex`, `--match-case`) reads each job's whole log, its rotated files included (`joblog.Each`, the port `ScanLog`), for the lines it matches, its newest 1000, each numbered in the whole log (`n`) and the job its line count (`count`); `--since` reads it from a time (RFC 3339), its first 1000 lines; followed, a search filters the lines followed. A job's detail also gives its folder and command (run.toml's `cwd` and `cmd`) and, for a docker compose stack its launcher left running, the command that follows its containers (`compose_logs`, `docker compose -p <project> logs -f`, the project the worktree's `COMPOSE_PROJECT_NAME`). Elsewhere, the read: `[job] text` per line (`[job · branch]` over several worktrees), a job named that never ran `= feat/a: never has not run`; with `--follow` (`-f`) the stream instead, unframed, what never ran said as the read says it, until the jobs ended, Ctrl+C or the reader leaving, exit 0; `--output json` is the read's envelope, with `--follow` a JSON object per line, typed: `line` (`worktree`, `job`, `at`, `text`), `absent` (`worktree`, `job` when one was named), `warning` (a warning's `code`, `message`, `params`, `follow_up`), and `error` (`error`, the envelope's), the last line of a stream a failure ends once it started (the exit code unchanged). `-q` silences the lines, never the warnings. At a terminal, the view shows the lines read of a job the daemon has none of (the legacy daemon keeps none).

## What run ps and run list read

`run ps` (`command/runps`, `run-ps` in the catalogue, `wtm-next run ps`) is a read of the jobs wtm's daemon runs on the whole machine, from any directory: its opener (`openRunPs`) opens no repository, and its use case opens each repository its jobs run for (`openProject`: the job's `repo`, else the main checkout a shared job runs in, else the worktree it runs in). `--repo <path>` (`domain.PathRepo`, read from where the caller stands) narrows it to one repository, refused `git.not_a_repository` (21) outside any; the web always sets it. An item per group, a repository after the other: each worktree running jobs for itself (subject its branch, else its path), the main one first, then git's order, then the repository's shared services (subject `shared`, `branch` and `path` the main checkout's, where they run); then every group holding a crash moves first, whatever its repository. A subject is unique within a repository only: a surface keys a group by its `repository` and `path`, and `shared`. A worktree whose only jobs are claims is no group: it shows among its shared service's `holders`. A group's detail: `repository`, `shared`, `branch`, `path`, the `profile` its jobs were started under, its `counts` by state, always each of them (`holders`, how many worktrees hold one of the shared services, 0 elsewhere), and its `jobs`: crashed, starting, running, then exited, stopped and not started, each in run.toml's order. A job: `name`, `kind`, `state`, `hold`, `url`, `address` (`localhost:<port>`: its url's port, else its one port; none for a runner, whose `services` carry theirs, run.toml's `runs` at the worktree's ports, each with its runner's `state`), `started_at`, `ended_at` and `duration_ms` of one the daemon ran that ended, the `exit_code` of a crash or a task, its `last_line`, `dir` and `command` (run.toml's `cwd` and `cmd`), its `log` file; a shared service its `holders` (`branch`, `path`, `namespace`, `since`: when the hold was taken, the service's own start for the main checkout's). The jobs of a group's profile the daemon does not list there are listed too: `stopped` once their log holds a line (the last one their `last_line`, whose `at` is their only time: the daemon no longer knows when they started nor ended), else `not_started`; a job a runner listed there starts itself stands as that runner (`run.StandingIn`, following nested runners as run up does, `project.Run.Children`; `repository.LastLines`; `run.Unlisted`: the rule status and run list read by too, status naming the runner a job stands as, `run_by`, and raising its crash once, on the runner). Warnings: `run-ps.jobs_unknown`, `run-ps.daemon_skew`, `run-ps.repo_unreadable` (a repository its jobs run for that does not read: its jobs listed without what run.toml says), and on a group `run-ps.meta_unreadable` (its record does not read: its runners' services have no address). A group's profile is that of its own jobs, up or ended. Its text draws a block per group, its repository named once the read spans several. The web's Running page lists it, `--repo` its repository (`jobsQuery`, which the sidebar's count shares): a group per item, folding on its header (the shared services folded by default), what ended closing it on a quiet row that shows it on demand; a search, the All / Running / Crashed chips and the Filter menu (its Worktree submenu: all, the shared services or one worktree; the states it lists), what they hide said in the toolbar; jobs pinned to the top. Folded groups, pins, ended jobs shown and the filter are kept per browser and per repository (`useUi`), a narrow window folding the list into the job switcher.

`run list` (`command/runlist`, `run-list`, `wtm-next run list [worktree]`) is a read of what run.toml declares as one worktree runs it: the one named, else the one the caller stands in (a terminal with none named asks it, the caller's first). Its detail: `branch`, `path`, the `profile` it runs, its `profiles` (`name`, `default`, `jobs`, `running`) and its `jobs` (`name`, `kind`, `state` there, null when the daemon cannot tell, `hold`, `dir`, `command`, the `ports` it binds there at the worktree's offset, `url` while up, `shared`, `runs`), each with its `actions`: a profile `run up` and `run down` of it (`run-list.up`, `run-list.down`), a job `run start`, `run stop` and `run logs` of it (`run-list.start`, `run-list.stop`, `run-list.logs`), each in that worktree. A record that does not read is `run-list.meta_unreadable` on the item, its ports unknown. No run.toml is `run-list.not_initialized` (25, followed by `run init`), one that does not load `run-list.run_invalid`. At a terminal its picker asks a profile or a job, then one of its actions, and ends on it as the follow-up the read prints.

In next, `--all` means every worktree of this repository (sync, fast-forward, exec, status, run down), never the machine; a command of the whole machine (run ps, wtm's daemon commands) narrows to one repository with `--repo <path>`, the one shared field `domain.PathRepo`.

## What run down stops

`run down` (`command/rundown`, `run-down` in the catalogue, `wtm-next run down`) stops the jobs wtm's daemon runs in worktrees: those named, else the one the caller stands in (a terminal opens the picker on it), or `--all` of this repository's (each worktree the daemon lists a job of, then each removed one whose jobs still run for it, never another repository's; refused beside a worktree or `--profile`, `run-down.all_narrowed`); a worktree is named by its branch or its path (read from where the caller stands, through its symbolic links, as git spells the worktree's root: `.`, `../feat-a`; two spellings of one worktree are given twice), or by the path of a worktree of this repository that git no longer lists whose jobs still run, a job there having been started for this repository (`Removed`, the follow-up of `clean.jobs_left`; another repository's directory is none of this one's, and a job whose start named no repository is refused saying so); a worktree named by a path is locked once the plan resolves it. `--profile` narrows the stop to that profile's jobs, those not running listed (`not_running`). It never needs run.toml: one that does not load is a warning, `run-down.run_invalid`, and what runs stops all the same. Its plan gives, per worktree, each job it reaches with its `fate` (`run.Fate`, decided over every worktree of the stop at once by `run.StoppingIn`): `stop` (a job of the worktree's own, a stack with the `stop_command` the daemon recorded, or a shared service whose every hold the stop lets go of), `release` (a hold on a shared service other worktrees keep, `kept_by` them, the main checkout among them when it holds it), `clear` (a job that crashed, cleared from the listing); a shared service a main checkout runs for the others without holding it is theirs, left out. A plan that reaches no job is empty. Its form never starts wtm's daemon; its plan starts one that died leaving processes in its index (`run.ErrUnknown`), to take them over, and is refused `run-down.daemon_unavailable` when the daemon started still cannot tell. One of another build is asked all the same, `run-down.daemon_skew` warned with the restart, and `run-down.fates_approximate` when a worktree stopped holds a shared service whether the main checkout holds which cannot be told: such a daemon does not list `main_holds`, `repo` nor `stop_command`, which are read from the index, a shared service the index has no record of left unknown (`run.Job.MainHoldsUnknown`). One of another protocol, or one holding jobs the client cannot go on with, refuses the stop, `run-down.daemon_skew` (precondition, exit 25), followed by the restart (`repository.SkewRefusal`). The worktrees stop at once, each between its unit's events, its jobs one after the other, its own first then its holds, each between the phase events of `job`, the lines a stack's stop command prints reported in its phase (`phase.output`); a stop sent is let finish whatever a Ctrl+C. Each item says what became of each job as the daemon answered its stop (`stopped`, `released`, `cleared`, `not_running`, `failed` with the daemon's message, `not_reached`; the legacy daemon's `released` read as such), the holds on one shared service the stop lets go of together each `stopped` once one of them stopped it; a job of `--profile` up in its worktree for the others is not `not_running`; a stop that fails fails its worktree (`run-down.stop_failed`, naming the jobs, exit 1) and stops none of the others. Its follow-up starts again, with `run up` and the profile they ran (that of their holds on shared services when those are all they ran), the worktrees still there that stopped or released a job (`run-down.up`). The web stops jobs from the Running page's Stop jobs (its picker shows the worktrees that run something), a group's stop button and its menu, and a worktree's menu and detail, which open on Confirm; the stop runs with no Cancel, a stack's row unfolding on its stop command's lines.

`run start` (`command/runstart`, `run-start` in the catalogue, `wtm-next run start [worktree] --job <name>`) starts one job of run.toml in a worktree, the one named, else the one the caller stands in, through run up's sequence (`runjobs.Service.Start`): `--job` is required (exit 2 when missing), its options run.toml's jobs, each with its `kind` and the worktree it is up in (`running_in`); a job run.toml does not declare is `not_found`. Its plan is run up's `Target` with that one job, its `action` `start`, `up` (a service up there, left as it is: an empty plan), `join` (a shared service, which runs in the main checkout; in the main checkout, one it runs for the others alone, which takes main's own hold: the undo of its release), or, with `--restart`, `restart`: the job stopped then started again within its `job` phase, keeping the profile it was started under; `--restart` always appends to the job's log behind the run mark (`run.Spec.Restart`), a job not up, or crashed, started with its log kept; a restart whose stop fails leaves the job `already_running` (`run-start.job_failed`), one cut short once it stopped leaves it `stopped`, followed by its start again (`run-start.start`); `--restart` of a shared service, from a worktree that holds it (a claim, or the main checkout's own hold), restarts it in place for every worktree holding it: the daemon stops it and starts it again, every claim and the main checkout's hold kept, its namespaces kept, its log appended; the plan names the worktrees it stops for a moment (`held_by`, the recap's "Stops for a moment in"), which the wizard shows before its confirmation and `--yes` takes as asked; its namespaces are not made again (`create` does not run), so a service whose storage does not outlive its process loses its databases on a restart; from a worktree that does not hold it while it is up elsewhere, `--restart` is refused (`run-start.restart_shared`, exit 2), and up nowhere it is started, as a start of it; a daemon of another build that cannot tell whether the main checkout holds it is taken as holding it, as run stop takes it. The others' jobs stop first as run up's (`--exclusive`, `--parallel`, run.toml's `concurrency`, else asked), never asked for a task (`domain.SkipTask`); a port another worktree holds, a job reaching foreign data and a skewed daemon holding jobs are run up's refusals (`run-start.<code>`), the last followed by the start forced; the drops owed a shared service it starts or joins are paid as run up's. Its job starts under no profile. The outcome is one item, its detail `path` and `jobs` (run up's statuses), followed, when the job is left up, by `run logs` and `run down` of the worktree (`run-start.logs`, `run-start.down`); a task that fails offers no stop. Its questions never start the daemon. At a terminal, a service it left up opens the live view on the worktree with the job selected; `-d`, a task, `--quiet`, `--output json` and a dry run end on the outcome. `status` offers it as the fix of a crashed job (`status.job_crashed`, with `--detach`).

`run stop` (`command/runstop`, `run-stop` in the catalogue, `wtm-next run stop [worktree...] --job <name>`) stops one job in worktrees: those named, else the one the caller stands in (a terminal opens the picker on it), named as `run down`'s are (`runjobs.Running`, shared with it). `--job` is required (`run-stop.job` missing is a usage problem, exit 2); its options are run.toml's jobs, in its order, then those wtm's daemon runs in the worktrees picked that run.toml does not declare, each with its `kind` and the worktrees picked it is up in (`running_in`); a job neither declared nor run there is `not_found`. One that does not load is a warning, `run-stop.run_invalid`, the job taken by its name. Its plan gives, per worktree, the job's `fate` as `run down`'s (none when it is not up there), with the same warnings (`run-stop.daemon_skew`, `run-stop.fates_approximate`), refusals and locks; a plan whose job is up nowhere is empty. The worktrees stop at once through `runjobs.Stop`; each item says what became of the job (`stopped`, `released`, `cleared`, `not_running` where it was not up, unchanged, `failed`, `run-stop.stop_failed`, exit 1, stopping none of the others, `not_reached`). Its follow-ups start the job again, `run start <worktree> --job <job>` per worktree still there that stopped or released it (`run-stop.start`), which the web's undo reads.

## The live view

`ui/runview` shows the jobs of some worktrees until the user leaves it, with `q` or Ctrl+C; leaving stops nothing. `run up`'s command line opens it at a terminal (stdin and stderr terminals, human output, neither `--quiet` nor `-d`) on the worktrees of a start that left a job up, once every job is started, then draws the outcome under it: the view changes neither the outcome nor the exit code. `cmd/wtm-next` hands run up's and run start's `cli` a `runview.View`, wtm's daemon of the machine (never started for the view), the browser, and the view's stop and restart; the `cli` gives the view each worktree of the plan with the jobs of its profile and the namespaces it holds in shared services, the main checkout's branch, the job the start launched first in its first worktree (where the cursor opens), and as its first notices the failures and the warnings of the start. A start a Ctrl+C cut short never opens it (exit 19). `run start` opens it on a service it left up, that job selected first (`Params.Job`); `run logs` (no start) reuses it, `s` and `r` doing nothing there.

- **The list**: the shared services up first, once each under `shared` (the main checkout's own job when the view covers it, else the first worktree's claim), then each worktree under its branch, the jobs its profile declares in their order (one the daemon does not know is not started), then the others the daemon lists there; a job of a worktree the view does not cover is not listed. Marks, font-safe: `•` up, `…` starting, `✓` a task done, `✗` failed or crashed, `−` stopped or not started; the uptime of a job up; the help row counts the jobs running. The daemon is listed every 2 seconds and on `ctrl+r`.
- **The pane**: the job selected only, attached (`attach`, sized to the pane, sized again on a resize) while it runs, or its log (`lines`, its last 1000) once it ended or for a stack its launcher left; a job not started says so. Its title: the job, its worktree (not for a shared service), its state from the daemon's listing (`running`, `joined, running in main`, `done`, `failed (exit 3)`, `crashed (exit 1)`, `detached`, `not started`), its URL or ports; on the right `live`, `history`, `focus` or `scrolled N lines back`. An attach or a log that fails is said once, in the pane and the help row, and asked again only once the job starts again, ends, or is selected anew. A stream the daemon ends while its job runs on (a client that fell behind) is attached again, once per start of the job, so a stream that ends at once is no loop; one that ended with its job keeps its pane. The emulator's answers to a job's queries (cursor position, device attributes) are dropped, never typed into the job: an attach replays old queries.
- **The band**: the notices the view opened on, each job that was up at a listing and has crashed or failed since, a stream that broke and a key the job's terminal refused (which ends the focus); a notice brings the band back once dismissed, and the pane and the job's terminal give it their rows; `esc` dismisses it.
- **The keys**: `↑↓`/`jk` the job, `pgup`/`pgdn` and `shift+↑↓` scroll back, `G` live, `/` the filter (enter applies; `esc` clears it, typed or applied), `s` stop the job selected (a shared service released) and `r` start it again (never a shared service, whose restart stops it for every worktree holding it: `db runs for every worktree holding it: run start --restart restarts it for them, once asked`), one at a time, through `Params.Stop` and `Params.Restart`, which `cmd/wtm-next` wires to run stop and run start `--restart` of that job in its worktree, run unattended (the others' jobs kept), what became of it a notice (`api stopped`, `api: nothing to stop here` when it was not up or its worktree does not hold the shared service, `could not restart api: …` with the refusal's command line that does it anyway, a start forced) and the jobs listed again; `q` waits for an action under way; Ctrl+C cuts it short (`leaving once restarting api… ends`), waits for it, then leaves, saying after the view what the user must know: an action that failed, a restart that left its job stopped, with the command line that starts it (`runview.View.Again`), or, the wait over (30 s) or Ctrl+C again, an action still under way and how to check it (a restart with `run start`, a stop with `status`, `runview.View.Show`, never a start of what was being stopped); `ctrl+r` list again, `o` open the job's URL, `a` where each job up answers, a shared service with the namespaces the worktrees hold in it (`esc` closes it, else clears the filter, else dismisses the band), `enter` focus, `q`/Ctrl+C leave. Focus types every key into the job, Ctrl+C included, until `esc` twice within 600 ms; it is refused for a task (no terminal) and for a shared service another worktree's claim reaches (`db runs in main: its output is read-only here.`), whose output still shows. The mouse: the wheel moves the list or scrolls the pane, a click opens the URL under it; URLs are OSC 8 links.

## What init writes

`init` (`command/initialize`, `init` in the catalogue: `init` is Go's name for a package's set-up) writes config.toml whole, from its settings as `service/settings` asks them: where worktrees go (`base_path`, `base_branch`), where a new worktree's .env files come from and which (`env_strategy`, `none` copying none, `env_files`), the hooks of a creation and of a removal (`on_create`, `on_clean`, each a `hooks` field: a command, the folder it runs in, whether a failure lets the next run). A first init fills each from what the repository suggests (`adapter/detect`: the .env files and their template, the install of the package manager package.json or a lockfile names, `docker compose down` for a root compose file; `adapter/git.OriginHead`, else the main worktree's branch); a re-init from config.toml as written, each .env file the repository holds listed but only those config.toml holds picked, so nothing removed comes back. Unattended, a flag changes its setting alone; a re-init that changes nothing writes nothing (`unchanged`). The plan names the settings, the file and, on a re-init, those that change (`changed`, each noted `(was …)` in the recap); its fingerprint covers the file it replaces, so a config.toml edited since the preview is a stale plan, and one edited between the plan and the write is refused `init.changed_on_disk` (conflict). A config.toml that does not parse is refused `init.config_invalid`, followed by `config edit`; one a newer wtm wrote `init.config_newer` (exit 22). The form falls in three sections (`worktrees`, `env_files`, `hooks`, `Form.Sections`). Once written, the repository joins the registry; the outcome follows up with `create`, `relocate` while worktrees sit outside the folder (a re-init that moves the folder warns `init.base_path_moved` instead, with `relocate`), and `run init` while run.toml declares nothing. A config.toml next writes is the legacy wtm's, comments included (`adapter/config/config.toml.tmpl`), and the legacy binary reads it. The global config is neither asked nor written.

## What exec runs, and what it holds

`exec` is a mutation in shape (a form, a dry run, a fingerprint, an operation on the bus) that changes nothing of wtm's state but its logs: a directory per worktree, `<state>/exec/<worktree>/`, and a log per run, `<op>.log`, which its run keeps flocked until the whole run ends (`shell.OpenRunLog`), so two runs in one worktree never mix theirs; each run first removes the logs of that worktree no run still holds. Its locks are shared, on the repository and on each target: two runs share a worktree, and a `clean` that would remove one, which takes it exclusive, is refused `lock.held` (exit 24) while the command runs, as the run is refused while the removal holds it. `lock.held` names what is locked (`scope`, `name`) and its holder from the record `adapter/oplock` keeps (`command`, `surface`, `pid`, `started_at`), `unknown` when none claims it (a legacy `wtm`, or a process gone); its message reads `feat/a is locked by clean, started from web (pid 4242)`.

Each target runs `/bin/sh -c <command>` through `shell.RunHooks`, as a chain of one hook: its own process group, reaped once the command returns (`HookChain.Reap`: what it left running in the background is stopped, where a hook may leave a server up on purpose), stdin closed, its stdout and stderr each split into lines of its own. Its environment is the one its hooks get: the process's own without `env.NotInherited` (the variables wtm sets in a worktree and the ports run.toml declares, which are the caller's worktree's, never the target's); plus, only under an isolation with a compose job and with an ordinal, the run environment its hooks get (`env.HookEnv`). exec never allocates an ordinal: a worktree without one runs without it, warned `exec.env_unnumbered`, and one whose record does not read (or a newer wtm wrote) runs without its run environment, warned `exec.meta_unreadable`. The command after `--` is a field like any other: `form.Words.Flag` `-- <command>` marks it trailing, `form.Command` reads it from the words after `--` and spells it last, after every flag (the retry, the dry run's apply line). The targets run at once, exec's own progress (`command/exec/cli/progress.go`, over `ui/output`'s line primitives) drawing a line per target as it ends. With `--quiet`, the failure of an apply names the subject it stopped at (`domain.Outcome.FailedAt`), since nothing else does, unless its message names it already.

## What config show, set and edit do

`config show` (`command/configshow`, `config-show` in the catalogue, `wtm-next config show`) is a read of config.toml as a document, `service/settings` with no request and no detection: its one item `config.toml`, whose detail is the settings as the fields of a form (`settings`: each with its value and origin, a closed select its values, its section, `domain.SectionsOf` their states, the problems the file holds), each setting's default and whether its value is it (`defaults`), the remembered answers (`remembered`: question, value, the entry config set's `remembered` field spells, and the `problem` an answer wtm cannot keep holds, its warning followed by `config edit` and drawn under its row), the file's `digest` and whether a newer wtm wrote it (`newer`, a warning `config-show.config_newer`); a value wtm can't use is a warning `config-show.invalid_value` on its setting (exit 0), a file that doesn't parse is refused `config-show.config_invalid` (exit 1) with where (`line`, `column`, `key`, `setting`) and `config edit` as its follow-up, no file `config-show.config_not_found` (exit 12, `init`). Its text draws a block per section, each setting its label, value, `· default`, the values a choice takes and what it does (the words `form.Settings` shares with init), then the remembered answers. `config set` (`command/configset`, `config-set`) is the mutation the web and the command line change settings with: a setting given replaces config.toml's (`settings.Given`, the flags init's), the others are kept, and a terminal asks none of them once a flag is given (`form.Command.KeptBy`, every field but `replaces`: each step left unanswered reads `kept` in the trail, asked still for a problem the flags make; no flag walks every setting); `remembered`, given, replaces the remembered answers whole, empty forgetting them all; `replaces`, given (flag only), is the `digest` config show read the change on, a file changed since refused `config-set.changed_on_disk` (409): the web's "changed on disk while editing". It refuses the problems of the settings it changes and those the change makes on another (`--env-strategy` with no `.env` file picked names `--env-file`), a problem another setting holds on disk already being left to its own change, and a file a newer wtm wrote (`config-set.config_newer`, exit 22) while its questions still read it; a remembered answer wtm cannot keep, written back as it is (left alone, or sent back in `remembered` as config.toml holds it, as a forget of another sends it), is a warning `config-set.remembered_kept` followed by `config edit`, never a refusal. Its plan is the `changes` (each field's values before and after, the recap listing `.env` files and hooks one per line, `RecapRow.Stacked` as init's) and the digest of the file it `replaces`, which the fingerprint covers, so a file changed on disk since the preview is a stale plan; its outcome ends on `config-set.undo`, the same command with the previous values of the fields it changed and `replaces` the digest of the file it wrote, so an undo after a hand edit is refused, and none is offered when the file cannot be read back (the web's Undo, the command line's next step). `config edit` (`command/configedit`, `wtm-next config edit`) opens config.toml in `$VISUAL`, else `$EDITOR`, else vi (`adapter/shell.Edit`: a shell word list, the file as its last argument, in the terminal's foreground group; no editor and no terminal refused), opening a file that doesn't parse too, to fix it; then reads what the editor left: a file that holds a value wtm can't use fails `config-edit.invalid` (exit 1) with a warning per problem, one that doesn't parse `config-edit.config_invalid` (exit 1), each kept as edited and followed by `config edit` again. Only a terminal runs it: it is out of the catalogue (`terminal` in `cmd/wtm-next`'s tests), the web's Settings page copying `wtm config edit`. The Settings page (`features/worktrees/settings/`) reads config show (again when the window regains focus: a hand edit sends no event), saves a choice and a forget at once through config set with an Undo toast, and a value or a list in its dialog, whose questions are asked with `replaces` the digest it opened on, so a file changed by hand is asked again rather than prefilled from the cache, its Save mine held to the file the page reads now; a save at once refused names each field's problem; a remembered answer wtm cannot keep shows its problem and `config edit` on its row.

## wtm's daemon

One process per machine, wtm's daemon (`wtm-next daemon serve`, hidden), runs the jobs of every repository, serves their named addresses and carries the event bus, on one socket, `<UserConfigDir>/wtm/wtm.sock`, under one lock, `wtm.lock`, the legacy daemon's: `cmd/wtm-next/daemon.go` wires `daemon.Daemon` (`internal/daemon`) over `adapter/process` and `adapter/daemon.Index`, and serves it with `adapter/daemon.Serve`, which takes the lock, listens and idles out, handing the bus's requests (`publish`, `subscribe`) to `adapter/events.Relay` and every other to `adapter/daemon.Server`. A daemon started while another holds the lock stops, `daemon.running` (conflict, exit 24), said in its log. A client that needs it starts it (`adapter/daemon.Daemon.Ensure`, `wtm-next events`), its standard error in `daemon.log` beside the socket; a read never starts it. It stops after 30 seconds with no subscriber, no request and no process of a job; detached stacks run without it and the next one takes them over.

- **The protocol.** NDJSON, one request per connection, every answer stamped with `protocol` (2), `version` (the build) and `pid`; an error carries a code, `daemon.<code>` (`run.Code…`). `list` (`work_dir` optional) answers the `proxy` (`port`, the port it bound, and `public_port`, the port a named URL announces, both 0 when it is off; read by LUC-352's `run proxy status` and the forwarder) and the jobs: `name`, `kind`, `work_dir`, `state` (`running`, `crashed`, `exited`, `stopped`), `hold` (`run.Hold`: `own`, a process of the daemon's; `detached`, a stack its launcher left; `claim`, a hold on a shared job another worktree runs), `reaped`, `pid` (`own` only, never one taken over from the daemon before), `started_at` (while up, and on a job that ended beside its `ended_at`, UTC to the millisecond; `jobs.json` keeps legacy's own), `ended_at` (when a job the daemon ran ended: crashed, exited or stopped), `namespace` (on a claim, and on a shared job whose main checkout holds it: the namespace it made for that worktree, `env.NamespaceFor` over the hold's start), `shared_dir` (the main checkout a shared job runs in), `main_holds` (on the shared job itself: whether that checkout holds it, beside the claims of the others), `repo` (the main checkout of the repository its start named), `branch` (its worktree's branch there, the main checkout's for a shared job's own run), `stop_command` (a stack's, as it was started), `exit_code`, `url`, `ports`, `last_line` (`at`, `text`: the last line it printed, from its log for a job taken over), and legacy's `status` word (`running`, `detached`, `joined`, `crashed`, `stopped`, `reaped`), which a legacy client counts the jobs a daemon holds by; `jobs` is `[]` when there is none. A client that stops reading is let go: a write it does not take within a second fails, and every later write to it is dropped. `start` (`spec`: the job of run.toml, the `profile` it starts under (listed with the job and kept in the index), `work_dir`, `env` and `unset` resolved by the client, `log_dir`, the directory its log is kept in, `origin`, `routes` (`job`, `host`, `port`: the variable of `env` that spells it), the names its proxy serves it under, and for a job of shared scope `shared`, its main checkout's `work_dir`, `env` and `log_dir`) sends the lines of a task or a launcher (`line`, `at`, `text`: sanitized, stdout and stderr one stream), then `ok` with the job or `error`; a foreground service answers once it is up. `stop` sends the lines a stack's stop command prints (`line`, as a start's) to a client that asks for them (`lines`; the legacy client, which takes its first answer that is no `output` as the stop's, asks none), then answers its `outcome` (`stopped`, `released` for a shared job other worktrees still hold, `not_running`) and, for a release, `released`, the legacy daemon's word, which a legacy client reads, `stop_all` each job with its own, `shutdown` stops the foreground services and leaves the stacks and claims to the index. `lines` (`name`, `work_dir`, `tail`, at most 1000, all it keeps when 0, `follow`) sends a job's last lines as `line` answers, then, with `follow`, each new one until the job ends or the client leaves, then `ok` with the job as it stands (`daemon.job_not_found` for one it does not know; a job taken over gives its log; `daemon.follower_behind` for a follower that fell 1024 lines behind, let go so it follows again); a line's `at` is RFC 3339, UTC, to the millisecond; the web relays it as server-sent events (LUC-361). `attach` (`name`, `work_dir`, `cols`, `rows`) answers `ok`, then carries the job's terminal raw both ways: up to 1 MiB of what it printed, what it prints, and what the client types, until the job ends or the client leaves; `resize` sizes that terminal again (`daemon.no_terminal` for a task or a launcher, which run through a pipe). A client refuses to attach to, or resize, a job of a daemon of another build or protocol, `daemon.skew`, as it refuses to start one; the legacy daemon's attach, the same shape, is taken. `publish` and `subscribe` are the bus's; the server hands `adapter/daemon.Server` the reader that read a request's line, so a client's first keys are never lost.
- **Skew.** `Ensure`, before a start: a daemon of this build is used; one of another build (`version`), another `protocol`, or the legacy wtm's (no `protocol`) holding no job up is asked to `shutdown` and replaced; one holding jobs is refused, `daemon.skew` or `daemon.legacy` (a daemon of another protocol counts every job it lists as held); the command that asked spells the follow-up, `daemon restart` (`daemon-restart` in the catalogue), as the adapter's errors carry a code and no command line. One that died leaving jobs in its index is taken over by a new one. A daemon is never signalled. Reads and stops take any daemon: the legacy daemon's listing is read as it spells it, and `Jobs` returns a `*run.Skewed` beside the jobs of a daemon of another build or of the legacy wtm, which `repository.Ask` turns into the read's `<command>.daemon_skew` warning, followed by the restart. A start that meets a daemon idling out (`daemon.stopping`) ensures a daemon and is made once more.
- **The index**, `jobs.json`, is the legacy wtm's, version 2, so a 0.30 daemon's jobs are taken over by next's and back: the foreground services (pid, group, start), the detached stacks and the claims up, the stack a launcher running again replaces among them, every key of a job's config as run.toml spells it (`probe`, `binds_no_port`, `runs` and `touches` included), and the `profile` a job was started under, which the legacy wtm drops; a newer version is left read-only: the daemon records nothing, silently (no restart brings back what it starts, no stack is taken over), which `daemon status` and the reads (`list`, `tree`, `status`, `run logs`: `repository.AskParams.FrozenIndex`) warn of, `<command>.index_frozen`. With no daemon answering, `Jobs` reads it: its stacks and claims are up, a foreground service left in it means a daemon died, and the jobs are unknown (`run.ErrUnknown`).
- **The run mark**: each start of a process for a job (a task, a service, a launcher; never a claim) writes `[wtm] started` first into its log and the lines its followers and the view read, once the process runs (a spawn that fails opens no log, so empties none), never as the job's last line nor among a crash's `last_lines`, nor handed to the start's client; a start with `restart` appends to the log, so the run before stays above the mark, and hands its readers the run before's last lines above it, as the log holds them. `run logs` marks that line (`mark`, in its read's `lines` and its stream's `line`), which the web draws as "Restarted 14:03:10".
- **A job's output** is cut into timestamped lines (ANSI, carriage-return redraws and control characters gone; stdout and stderr one stream), the last 1000 (and at most 1 MiB of their text) kept for `lines`, each written to `<log_dir>/<job>.log` (`2026-10-31T12:00:00Z  text`, the legacy wtm's format: one file per run, a stack launched again appending, rotated past 5 MiB with two backups; the files 0600, a legacy one narrowed as it opens; a directory made for them 0700, and so a legacy one holding the job's log, any other directory a start names keeping its mode), and handed to each follower; its raw bytes, the last 1 MiB while it runs, to each client attached. Its buffers are cut back once they doubled their caps, never on each write; the log and the start's client are written outside its lock, and the listing reads the last line with none. A follower or a client attached that falls behind is let go. What clients type into a job's terminal is queued (64 writes) and written by one goroutine per job, so a job that never reads holds no client; what overflows is dropped. `joblog.Last` reads the end of a log, the whole file only for more lines than that end holds; a daemon starting reads them before it takes its lock.
- **Recovery**, each start (`Daemon.Adopt`): a foreground service whose group is alive and started when its record says is reaped (SIGTERM, then SIGKILL while it is still alive) and listed `stopped`, `reaped`; one whose group is gone is `crashed`; one whose group belongs to another process now, or to the daemon itself, is dropped, never signalled.
- **A stack launched again** stays the worktree's while its launcher runs: indexed, given back if the launcher fails or is stopped. A shutdown hands it to the next daemon, and so a stack whose first launch it interrupted, which may be partly up; a client's stop kills the launcher, then runs the stack's stop command, the stack listed stopped and leaving the index only once that command succeeded; one still running after 5 minutes, or once the daemon stops, is stopped and fails the stop, `daemon.stop_failed`, the stack left up, indexed and served, so a start waiting on it never waits forever (legacy left it unbounded).
- **The process.** The socket is created under a narrowed umask, then made 0600: a request on it runs a command as this user. `daemon.log` is emptied by the daemon that took the lock, never by one losing the race. A failed accept is retried with a backoff; only the daemon stopping stops its jobs.
- **A shared job** (`scope = "shared"`) runs once, in the main checkout its start names, under that checkout's key; each other worktree asking for it posts a claim beside it, so the job table is its reference count, and the main checkout's own hold is a flag of the job (`main_holds`). A start with no main checkout is refused, `daemon.no_main_checkout`, never run once per worktree. Once held, the job's namespace (`[job.namespace]`, `env.NamespaceFor`: none under the verbatim isolation) is created for the worktree asking, its `create` run in that worktree with `WTM_NAMESPACE`, retried every second while the service comes up, no attempt starting after 30 seconds (legacy's budget), an attempt stopped once it ran 5 minutes (a bound legacy lacked: a database made from a large template takes more than 30 seconds) or once the daemon stops, and noted in the service's log (`[wtm] namespace app_feat_a ready for feat_a`); a namespace that cannot be made takes the hold back, and the job with it when nobody else holds it, `daemon.namespace_failed`; a start whose hold went while its namespace was made (the job ended, or the worktree let go of it) fails, `daemon.launch_failed`, and leaves any newer hold of its worktree alone, as does one whose job ended as soon as it launched it (a shared task). A start with `restart` from a worktree holding it (its claim, or the main checkout's own hold) restarts it in place: the job stopped, then started again from that spec, its claims waiting the restart out rather than dropped (a start of another worktree waits for it too), the main checkout's hold carried over, its namespaces neither dropped nor made again; a stop or a release of it meanwhile waits for the restart's end, re-checked under the lock it then acts with, with no bound of its own (as a start waiting on a stop: a restart ends once its stop and its start answered); a start that fails drops the claims left on nothing, except as the daemon stops, which leaves them to the index. A stop of a claim, or of the job from its main checkout, lets go of it: the job stops only once nobody holds it, `released` otherwise, and a start asking for it while it stops, or while its launcher runs, waits for that end before it claims it or starts it again; its namespace stays (stopping is not destroying: `clean` and `prune` drop it with the worktree). `lines` and `attach` of a claim reach its job: a worktree attached to its claim types into the terminal of the job every worktree shares (the run view of LUC-339 decides whether a claim attaches read-only). A shared job that ends on its own takes its claims with it (its events naming the worktrees that held it), and a daemon starting drops the claims on a shared job no longer up; a hold a failed namespace took back was never announced, nor is its end. `stop_all` releases the shared jobs after the others, one at a time; a shutdown halts the processes and leaves the claims to the index, and a start it cuts short stops no stack.
- **The proxy** (`adapter/proxy`) runs in the daemon's process, bound once it holds its lock and before it takes the index over, closed before it lets the lock go, so the next daemon binds the same port; on the global config's `[proxy] port` (11080 by default, none when `enabled = false`; `--proxy-port` overrides it, 0 turning it off), or the first port within 16 above it that is free and that a browser opens. It serves each service up under the names of its `routes` (a runner's children included), on `localhost` at the port its `env` spells: a foreground service from its start, a stack once its launcher succeeded (the names of the stack it replaces withdrawn) and again when a daemon takes it over, until it ends or its stop command succeeds, only the names it served withdrawn, never those a newer stack of its worktree, or another job, took over since; a claim serves nothing of its own, its shared job serves the one name a shared job has. The host goes through as the browser asked (cookies stay apart between worktrees), with `X-Forwarded-*` written afresh (a client's own, and `Forwarded`, dropped), websockets upgraded, a connection left idle closed after 2 minutes; an unknown host is answered 404 with the names served, only to a name of this machine (a page of another site whose name it rebound to the loopback reads none), a job that does not answer 502. A job's `url` is then its own route's name on the public port, without a port when that is 80: probed on every answer (`probe.wtm.localhost`, `X-Wtm-Proxy` with the port, `X-Wtm-Proxy-Token` with a token drawn at the daemon's start, so an unrelated server on port 80, or a stale proxy, is never taken for this one; a process of the user's that reads the token from the proxy and echoes it is outside what it guards against), never cached, so installing the port-80 redirection (LUC-352) takes effect at once. While its proxy serves a name the daemon never idles out: that would take the name down while the stack behind it runs. A port it cannot bind, or a global config it cannot read, is said in `daemon.log` and every job answers on its own port: a daemon refusing to start would refuse every job.
- **Job events**, `job.started`, `job.stopped`, `job.crashed` (its exit code and last 10 lines), `job.exited`, each naming the job's `hold` and, for a shared job, the worktrees holding it (`held_by`), a claim announcing its own start and release, are published by the daemon itself on the bus it carries, under the repository its client named; `wtm-next events` relays them.

### Its commands

`wtm-next daemon status|stop|restart|stop-jobs` (`command/daemonstatus`, `daemonstop`, `daemonrestart`, `daemonstopjobs`; `daemon-status`, `daemon-stop`, `daemon-restart`, `daemon-stop-jobs` in the catalogue) are the machine's, not a repository's: their opener ignores the directory it is given, their operations take the machine's one lock (`domain.MachineLocks`, in the daemon's directory: two of them take turns) and publish no event (`machineOperations`), and a test of the catalogue lists them apart (`machine`). The legacy wtm spells them `wtm run daemon …` (departure: at the root). Each reads the daemon through `adapter/daemon.Daemon.Status` (`run.Daemon`: whether one answers, its stamp and skew, its jobs, or the stacks and claims its index holds when none answers, its proxy, its socket, its index and whether it is frozen) and reports the jobs by repository and worktree (`run.Held`, `run.HeldRepo`; a claim the legacy wtm recorded with no origin placed beside its worktree's jobs, `run.Placed`).

- **`daemon status`**, a read: one item, the daemon (running or not, its pid, this build and the daemon's, its protocol and skew, its jobs by repository, the services a daemon that died left in its index (`left`), its proxy, its socket and its index), warned `daemon-status.index_frozen`, `daemon-status.daemon_skew` and `daemon-status.jobs_left` (each followed by `daemon restart`). It never starts the daemon.
- **`daemon stop`**: what a shutdown does to each job up (`run.ShutdownOf`): the processes the daemon runs stop, a shared job's own run among them (`stops`); its stacks run on, taken over by the next daemon, as the claims on a shared stack (`kept`); the claims on a shared job that stops go with it (`lost`: the next daemon drops a claim on a job down). No daemon running: nothing to do.
- **`daemon restart`**, as pm2 does: it reads the index before the shutdown (`Records`), shuts the daemon down, `Ensure`s one of this build, which takes the stacks over, then starts each service again from its record (its profile, worktree, environment, routes and log directory as they were, the restart's correlation ID), the shared ones last through the worktrees that hold them (a shared job's own run its main checkout does not hold comes back with its holders; the index keeping a shared job's main checkout and not where it runs, `Shared` is rebuilt from the record of that run); a start the new daemon finds up is back. A task running is cut, not run again (`tasks`); a job with no record, a frozen index's every job and stack among them, cannot come back (`unrecorded`), nor one whose worktree was removed (`gone`); each job that did not come back fails the item, `daemon-restart.not_back`, the others back; a new daemon that does not start fails it, `daemon-restart.start_failed`. From the shutdown on it runs shielded (`shell.Shield`): a first interrupt reaches nothing, a second waits for it, so the jobs it stopped are never left down; a daemon slow to stop (`daemon.stop_timeout`) is waited for by `Ensure`. No daemon running: one starts, and the services a daemon that died left in its index come back, the new daemon reaping their processes first. A daemon whose index a newer wtm wrote is a newer wtm's: restarting it as this build, a downgrade, is refused, `daemon-restart.downgrade` (refused, exit 23), unless `--force`, then confirmed. The plan names the daemon's build and this one, what comes back, what is taken over and what is not.
- **`daemon stop-jobs`** (`--repo <path>`, a path in a repository, relative to where the caller stands, `domain.PathRepo`): every job of every repository, or of one, stops through `runjobs.Stop`, each worktree a unit (`<branch> (<repository>)`), its stacks by their stop command, its holds on shared services after its own jobs (a shared job's own run let go of by its main checkout and by every worktree holding it, so that it stops with its last hold), a crashed job cleared; the daemon and its proxy stay up. A worktree that did not stop is followed by the same request again (`daemon-stop-jobs.again`). A shared service's own run that the stop lets go of names the worktrees that lose it (`held_by`, `runjobs.StopJob.HeldBy`), the web's "feat/a loses it". A daemon whose jobs cannot be read (another protocol) is refused, `daemon-stop-jobs.daemon_skew`.
- The machine's lock serializes `stop`, `restart` and `stop-jobs`, not `run up`, `run start` or `run down`, which take their worktrees' locks: a start meeting the daemon a restart stops is answered `daemon.stopping` and ensures the next daemon, then is made once more, and a job started before the restart reads the index is in it and comes back. With no user config directory there is no socket either: the lock is not taken, and the run warns its locks unavailable.
- `stop`, `restart` and `stop-jobs` confirm only a plan that cuts a job the daemon runs (`plan.confirm`, `form.Command.Unasked`): a stop of stacks alone applies at once. Unattended (no terminal, `--output json`) they apply without `--yes`, as every next/ mutation does; the legacy wtm refused "pass --yes" (departure).
- **The cutover.** The first 0.31 `wtm` finds a 0.30 daemon running: the reads list its jobs (`daemon_skew`, legacy), a start is refused with `wtm daemon restart`, which reads its `jobs.json` (the same version 2), shuts it down (it knows `shutdown`), starts a 0.31 daemon that takes its stacks over, then starts its services again: no job is lost. Run `wtm daemon restart` once after upgrading.

## Cancellation

- **Every child process runs in its own process group**, git included, and wtm signals the whole group itself: SIGINT, then SIGTERM, then SIGKILL, bounded by `exec.Cmd.WaitDelay`. The terminal's Ctrl+C therefore never reaches a child directly: `git worktree add` would otherwise undo itself on SIGINT while wtm records the worktree, and a hook would receive SIGINT twice.
- **The first Ctrl+C**, or SIGTERM, or SIGHUP (the terminal closed; not under `nohup`, which ignores it on purpose), cancels the operation: the worktree being added finishes its add, env copy and meta record (a shielded section), its hooks are stopped, and the later worktrees are skipped as interrupted. In human mode it prints `Cancelling — finishing <step> of <branch>; Ctrl+C again to stop now` on stderr. The command exits 19.
- **The second Ctrl+C** stops at once: the running children's groups are killed and the command exits 130.
- **A detached caller** (the web server, a desktop shell later) passes the use case its own operation context, never a request's: a client that disconnects does not cancel the operation, an explicit cancel acts as the first Ctrl+C and a forced one as the second. The forced one kills the children of every operation of the process already cancelled (`shell.KillCancelled`): it is process-wide, never one operation's, and never touches an operation nobody cancelled.

## The web server

`wtm-next ui` (`cmd/wtm-next/ui.go`) opens the web interface on the repository of the current directory: it reuses the server of this machine when one of its version answers, asks one of another version to stop (`POST /api/stop`, then it waits for its lock; one finishing an operation refuses, and ui names the operation rather than wait; one too old to be asked, ui names its pid for the user to stop, never signalling it) and starts one when none answers (`wtm-next ui serve`, detached, hidden), then prints the page's address, `http://127.0.0.1:<port>/#repo=<id>&token=<token>`, and opens it unless `--no-open`, through `web.html` (mode 0600), a page that redirects to it, so that the token never shows in the browser's command line. The page is the web front (`next/web`, docs/dev/web-front.md), embedded in the binary; a binary built `-tags noui` serves a page saying it has none, its API unchanged.

- **One per machine.** The server holds `web.lock` while it serves and writes `web.json` (its pid, port, version and token, mode 0600) beside `repos.json` (`adapter/webserver`). `web.json` is trusted only while `web.lock` is held: once its server stopped, the port it names may be anyone's, which never gets its token; no process is ever signalled by the pid it records. It listens on 127.0.0.1, on port 4777 when free so the page keeps its origin, else on one the system picks. It is no part of wtm's daemon nor the event bus. It stops after 30 minutes with no request in flight (an open event stream is one, a running operation too): new requests are refused, the event streams end, the operations running finish.
- **The guard.** A `Host` other than `127.0.0.1` or `localhost` at the server's own port is refused (DNS rebinding); under `/api`, an `Origin` other than the page's is refused and the token of this start is required in `X-Wtm-Token` (401 otherwise). No CORS header is ever written. The token travels in the fragment of the page's address, which the browser never sends; the page keeps it in `localStorage`, so that a tab a new start opens hands its token to the tabs already open (the `storage` event).
- **The routes.** `{repo}` is the id of a repository, a digest of its common directory (`web.RepoID`), resolved against the registry.

| Route | Answers |
| -- | -- |
| `GET /api/version` | `{"version"}` of the binary |
| `GET /api/repos` | the repositories wtm knows: `[{id, root, common_dir}]`, those no longer initialized pruned |
| `GET /api/repos/{repo}/commands` | the catalogue: `[{name, form}]`, each form outside any repository |
| `POST /api/repos/{repo}/commands/{name}/questions` | `{"answers": [{path, values}]}` → the form as the repository stands |
| `POST /api/repos/{repo}/commands/{name}` | `{"answers", "dry_run", "expect_fingerprint"}` → the v2 envelope, the status of its error's kind (400 invalid, 403 refused, 409 conflict, 412 precondition, 499 cancelled, 500 internal); with `Accept: text/event-stream`, each event as a line of the event stream (`domain.Line`: `v`, `type`, `ts`, `repo`, `correlation_id`), then the envelope as the event named `envelope` |
| `DELETE /api/repos/{repo}/operations/{id}` | cancels the operation, as a first Ctrl+C; `?force=true` then kills as a second; 202 |
| `GET /api/events` | the event stream of every repository, `?repo={repo}` of one: its lines, `warning` events (`web.Warning`: its `message`, and a `code` for an attempt that failed, `daemon.start_failed` when wtm's daemon did not start, else `events.bus_lost`: the stream is not ready until its next `ready`; a repository skipped has none), and `envelope` when it ends on a failure; a refusal before any line keeps its status |
| a route under `/api` asked with another method | 405 `web.method_not_allowed`, `Allow` naming the methods it answers; a path no route takes, 404 `web.not_found` |
| `GET /` and any other path outside `/api` | the page: a file of the front's build, `index.html` for a route of the front (`no-cache`), a hashed file under `/assets/` cached for good, 404 for one that is not there; the token is not required |
| `GET /api/repos/{repo}/jobs/{job}/logs` | the lines of the job of the worktree `?worktree=` names (`runlogs.Watch`, `Params.Logs`): its last lines then each new one until it ends (`?follow=false`: the last ones alone), or what of its whole log `?search=` (`?regex=`, `?match_case=`) or `?since=` reads; each event a line of JSON its `type` names (`web.JobLine`: `line`, `absent`, `ended`, `warning`), `envelope` when it ends on a failure; a refusal before any line keeps its status |
| `GET /api/repos/{repo}/jobs/{job}/log` | the job's log file to save (`?worktree=`, `Params.LogFile`), `text/plain`, an attachment `<job>.log`; 404 `web.log_missing` for a job that keeps none |
| `GET /api/daemon/log` | the log of wtm's daemon to save (`Params.DaemonLog`), `text/plain`, an attachment `daemon.log`, where a daemon that did not start says why; 404 `web.log_missing` when it keeps none |
| `GET /api/schema` | the published schema of the API, `api.v2.schema.json` (`api.Schema`); a server given none answers 404 `web.schema_unavailable` |
| `POST /api/stop` | stops the server as its idle stop does, 202; while operations run it refuses, 409 `{"operations": [ids]}`; once it accepted, a command is refused 503 `web.stopping` |
| `POST /api/command-line` | a follow-up → `{"argv"}`, as the command line runs it, for one the catalogue cannot run |

- **A browser's stream.** `EventSource` cannot send a header: a page reads `/api/events` and a command's progress with `fetch` and a streamed body, the token in `X-Wtm-Token`, never in a query string.
- **An operation's id.** The server makes the correlation ID of each POST of a command and answers it in `X-Wtm-Operation`, written before any event on a stream, so an operation can be cancelled while it plans; it is the `{id}` of `DELETE` and the `correlation_id` of its events, on the progress stream and on the bus. The operation's own `op` arrives with its envelope. A client that leaves loses the envelope: the bus keeps `operation.finished` (`ok`, `code`) under its correlation ID, and the reader reads `list` again.
