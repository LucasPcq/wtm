# Talking to the server

Everything that reaches `wtm-next ui`'s server lives in `src/api/`: the generated types, `fetch.ts`, `token.ts`, and one `queries/<resource>.ts` per resource (`version`, `repos`, `commands`, `operations`, `command-line`, `events`). Nothing sits between a component and TanStack Query.

## The token

`wtm-next ui` opens `http://127.0.0.1:<port>/#repo=<id>&token=<token>`. `takeFragment()` keeps the token in `localStorage` and drops the fragment from the address. Every request carries it in `X-Wtm-Token` (`request()` in `fetch.ts`), never in a query string. All tabs of the origin share it; a restarted server's new token reaches them through the `storage` event, and a token change reloads the page so that a server of another version serves its own code. A page with no token says how to open it.

## Reads

| Query | What | Key |
| -- | -- | -- |
| `readQuery(repo, 'list' \| 'tree' \| 'status', answers)` | a read of the catalogue, without GitHub | `['repo', id, …]`: every event of the repository invalidates it |
| `githubQuery(repo, command, answers)` | the same read asking GitHub (`with_prs`) | `['github', id, …]`: no event, no reconnect invalidates it; `staleTime: Infinity` |
| `questionsQuery`, `questions()` | a command's form | under `['repo', id]` |
| `dryRunQuery(repo, 'create', answers)` | what an apply would do, its plan and fingerprint | under `['repo', id]` |
| `commandLineQuery(followUp)` | a follow-up as the line to type, `undefined` when it cannot be spelled | `['command-line', followUp]`, never stale |

Every envelope is typed by `narrowed()` in its `select`: an item's detail is the command's (`Read<'list'>`, `Applied<'create'>`), and `undefined` when the item was not read (a failed or cancelled item carries `{}`). A row of such an item says "not read" or "unreadable", never crashes on a missing field.

**GitHub on demand.** Each view asks GitHub once, the view on screen only: `useRead(repo, 'list' | 'tree', enabled)` holds a view's live and GitHub reads, and the Worktrees page enables only the one on screen. The detail asks each time it opens (`refetchOnMount: 'always'`). Fetch origin (`fetchOrigin`, a list read with `fetch` only) then invalidates both `['repo', id]` and `['github', id]`: the reads on screen ask again, one per view; one off screen asks when it shows. Never `with_prs` on an event, never a timer.

**Something that only counts** (the sidebar's worktree count) observes a read with `enabled: false`: it shows what the view on screen read last, and costs no read of its own.

## A worktree's condition

Each read, live or GitHub's, publishes a worktree's `condition` (`no_worktree`, `deleted` (a virtual root whose branch no longer exists), `unreadable`, `missing`, `rebasing`, `merged`, `changed`, `clean`, the first that applies, ranked in Go) and its `actions`: every action of the worktree, each offered with its follow-up or refused with the code of why (`worktree.Unoffered`). The screen maps a condition to its look (`conditionLook`); every menu (a row's context menu and its "⋯", the detail's, the selection bar) renders the one list of `features/worktrees/utils/actions.ts`, disabling in place what the core refuses or the web does not run yet. Over the two reads of one worktree there is one rule, `overlaid(live, github)` in `features/worktrees/utils/condition.ts`, used by the list, the tree and the detail: it returns the GitHub read when that one says merged and the live one says changed or clean, the live read otherwise. The detail then shows the winning read's problems.

## Follow-ups

A follow-up the catalogue cannot run (sync, go, run …) shows as its command line to copy: `CommandLine` (`features/worktrees/components/command-line.tsx`), a block or `inline`; a menu of them, `ActionsMenu`. One the server cannot spell says so with what it meant (`No command line for this: …`), never disappears.

## Operations

`runStreamed({ repo, command, call, started, line })` (`queries/operations.ts`) posts a command with `Accept: text/event-stream` and `expect_fingerprint` from the dry run. It hands the operation's id to `started` as soon as the server names it (`X-Wtm-Operation`), each event to `line`, and resolves with the narrowed envelope. An answer that names no operation is refused and its connection aborted: nothing could cancel it. `cancel(repo, operation, force)` is `DELETE …/operations/{id}` (`?force=true` the second time).

A mutation's run lives in one zustand store, keyed by command and repository (`useRun(repo, command)`, `useUnderWay` in `features/worktrees/hooks/use-run.ts`): the dialog shows it, closed and opened again, and the list dims the rows it works on. Each command turns its plan into units (create's `planned`, a fast-forward first; clean's `unitsOf`, one per worktree removed, both through `todo()`) and starts the run with them (`Start`); the shared `utils/progress.ts` turns each event into their phases, and `ending()` says how a run ended: cancelled (an item cancelled, or the envelope's error of kind `cancelled` when only the plan was under way), failed with why, or done. The dialogs share their frame and their pieces in `features/worktrees/components/`: `RunDialogContent` (the 24 px frame, one size while a run is under way, no close button then), `DialogBand` (the stepper or the progress bar, ruled off from the body), `DialogScroll` (the only scrolling area, never a native scrollbar), `ItemList` (the worktrees or branches a dialog is about, one bordered group of shadcn `Item` rows), `Details` (what most people never read, one click away: a plan's folders and hooks through `Facts`, a run's steps), `RunSteps` (the timeline while a run is under way; once it ended, folded last as "N steps · T"), `RunOutcome` (what a run did, in the groups "failed", "to check", "done", a lone group unnamed, each problem one line whose output or fix folds under it, its fix copyable from the line) and `RunningFooter` (Hide, Cancel, then Stop now). Each command keeps its own titles and words (`outcomeWords` in its `words.ts`) and maps its envelope into the outcome's groups in `utils/recap.ts`. A disabled button that has a reason says it in a tooltip on a wrapper, since a disabled button fires no pointer event.

## Clean

- **Selection**: rows are checked in the table (`useSelection`, every row but the main worktree's and one a run works on), the header's box checking them all and showing when only some are; the selection is what the rows on screen check, so a row filtered out of view leaves it. While some are, `SelectionBar` stands in for the toolbar, its destructive action last and apart. The detail's "…" menu runs clean's own follow-up as "Remove worktree…", on that worktree alone; both open the one `RemoveDialog` of the page (`useRemoveDialog`).
- **Steps**: Worktrees, Children, Confirm. The first reviews a forced dry run of every worktree asked, so each unsafe one shows what keeps it (`blockers`) and asks keep it or remove anyway; the request is the worktrees not kept, forced when one is removed anyway. Children is skipped when no child is left behind; its one choice is `reparent_children`, each child listed under the parent that goes with where it lands (`moves`). Confirm and the apply hold to the dry run of that request; a choice plans again, and the buttons wait for the fresh plan. A plan that cannot be made shows why; a worktree read again unsafe on a later step brings the wizard back to its choice (the step is derived, the state is one `useReducer`). One removal at a time: opening Remove while one runs, or while one that failed even in part is still to be read, shows it, and the rows checked meanwhile wait; a run that ended well is dismissed when Remove opens again (`openRemove(repo, worktrees)`, `dismissSucceeded`), so the next one opens on its own worktrees. Its failure (a stale plan) shows as the envelope's error; a run that removed every worktree asked takes the rows it opened on out of the selection, one that removed some takes those out (`useSelection().drop`).

## Fast-forward, and a run at once

- **Direct run** (`hooks/use-direct-run.ts`, `useDirectRun(repo, command)`): a quick, reversible action on one row (the row's menus, the detail callout) takes the command's run in the store at the click (`useRun().claim`, read from the store, not from the last render), so the row is under way at once and a second click, on any row, opens the run under way, or a failed one not yet read, on that run's worktrees, instead of starting another; a cancelled run counts as read, its toast said so. It resolves on the run's envelope once it ended (undefined when it never ran), so runs of one command can follow each other, and its toast takes an `action` and a `cancel` (Sonner's two buttons). It asks its dry run, never from the cache, then applies under that plan's fingerprint with the apply's own answers (`applying`: fast-forward's adds `no_fetch`, so the apply reads origin as the dry run fetched it). A Sonner toast goes from loading to success, to an error whose Details opens the dialog on the outcome, or to a plain one for a cancelled run; none when the dialog already shows the run. A plan with anything to decide (a refusal, any warning, no unit to run) releases the run and opens the command's dialog on Confirm instead, whose review asks a second dry run (two fetches of origin on that path, accepted: it is the uncommon one).
- **Entries**: one row runs at once, unless the reads on screen show it dirty: it then opens the dialog on Confirm without a dry run, so no unforced request ever names it; several (the selection bar) open `FastForwardDialog` on Confirm, the rows that do not offer it under Left as they are; the header's Actions opens it on the Worktrees picker, its options and default pick (behind origin, as last fetched, but those with a change) from the form's `worktree` field.
- **The safety rule**: the precheck sent untouched sends no worktree, so the command picks and keeps an unsafe worktree (its `fast-forward.kept` warning on its row, then in To check). Otherwise the request names the rows checked, with those the plan leaves as they are (never a behind one: only a behind worktree can be unsafe), so the outcome says why each stayed, forced only when the person checked an unsafe row under that very risk; a named unsafe row starts unchecked.
- **One fetch per flow**: the review (forced over the worktrees named, or the command's own plan) fetches origin; every plan made again on a tick and the apply send `no_fetch`. "Where each moves" reads the review's advances of the rows checked, so it follows a tick before the plan made again lands; an empty plan is the core's `plan.empty`. The plan made again is `planQuery`, keyed on the review's answer (`readAt`: its `dataUpdatedAt`), never stale, and out of `['repo', id]` and of the reconnect's invalidation: an event or a reconnect refreshes the review alone, and the plan follows on the choices of the review that landed, never on those of the one whose facts are gone; the button waits for both, and for `consented`, the plan having seen a change the review has not yet. An apply refused as `fast-forward.unsafe` (a worktree changed since the plan) ran nothing: `changedSincePlan` (`utils/changed.ts`) turns it into the wizard's notice on fresh rows, and the run is read once the dialog closes. The words are Records over `FastforwardStanding`, `FastforwardBlocker`, `WorktreeDivergence` and `WorktreeOperation` (`fast-forward/utils/words.ts`).

## Reparent

- **Steps** (`reparent/`): Worktrees (from a selection only, the rows that can't move under Left as they are with the list's `refused` words), New parent, Confirm. Every fact is a reparent question: `worktree`'s options carry each worktree's `parent` (and `gone`), `to`'s options are the parents it may take (the `pinned` base branch first) and `to.refused` the ones it refuses, as field errors worded in `reparent/utils/words.ts` (`self_parent`, `reparent.cycle` with its `under`). Confirm is the dry run's `moves`: one already on the parent goes under Left as they are, and an empty plan disables Reparent with why.
- **At once** (`hooks/use-reparent-now.ts`): a move the core spelled with its `to` (a Tree drop, a callout's fix, a child left orphaned by Remove or Prune, an Undo) runs through the direct run, one run per new parent (`byParent`), one after the other, and one toast for them all: Undo runs the core's `reparent.undo` follow-ups the same way, "Copy wtm sync" the `reparent.sync` ones merged. A dry run that refuses (a cycle) ends on an error toast saying why, whose Details opens the dialog on Confirm.
- **The Tree** asks reparent's questions with no answer for the nodes that move (their grip) and, from the grip's hover or focus, with the dragged worktree for where it may land (`tree/utils/targets.ts`): an option takes the drop, a refusal says why while hovered, the current parent is neutral, a branch reparent does not know is deleted. A drop before the answer lands runs all the same: its dry run refuses what the answer would have.

## The event stream

`eventsQuery` (`queries/events.ts`) is a `streamedQuery` over `GET /api/events`, read with `fetch` (`EventSource` cannot send the token header) and parsed by `EventSourceParserStream`. A line of a repository invalidates `['repo', id]`; `repo.added`/`repo.removed` the list of repositories; back after a break, every query but GitHub's is read again. It reconnects every 2 s once it ended or failed, and stops when the server refuses the token. It also keeps the operations under way, from any surface (`operations`, by `op_id`): a worktree is under way from its `unit.started` to its operation's `operation.finished`, which `useUnderWay` merges with the runs this page started, greying the row and closing its menu. A unit of an operation whose start the stream missed (one running when the page opened, or across a reconnect) is under way all the same, its command unknown; the bus names no subject before its unit starts, and an operation is under way no longer than the core's 10-minute cap, since a process killed mid-way never says it finished. `connectionOf` gives live, reconnecting, connecting or disconnected, which the sidebar's footer shows with the stream's warnings.

## Forms over a command's questions

`useCommandForm` (`components/command-form/`) builds a TanStack form from a command's `domain.Form` (`POST …/questions`): one value per field keyed by its escaped path (the form library reads `remember[0]` as nested), a text list as its raw text split when sent. The core validates: a change asks the questions again once typing pauses, `check()` asks at once, and only the latest answer is kept; the answer is the form shown (a field it no longer asks, a default that followed another answer) and its problems land under their fields once touched. The front re-encodes no rule (required, allowed options, branch names). Only the fields the person changed are answered, so a default or a remembered answer stays the core's to decide.

`CommandFields<P>` draws each field in its screen's words, a `Record<P, FieldWords>` over the paths of the fields it is given (`(DomainField & { path: P })[]`), which the core never gives: label (with Remember on the right when the core lets it be remembered), the input of its kind (`FieldInput`), where an untouched answer came from (from config, remembered), the help, the problems.

## Create

- **Words** (`create/utils/words.ts`): exhaustive Records over create's question paths (`createWords`), each closed select's values (`envFrom`, `isolation`, …), the skip codes (`skipWords`, `null` for a reason that means nothing in a browser), the plan's actions and phases. A question, option, reason or phase the core adds fails the build until it has words. The steps narrow the form's fields once to the screen's questions (`DomainField & { path: P }`), so `CommandFields` and `NotAsked` index the words directly, never falling back to the path. An option of no words is data (a branch) and reads as its value; its facts (`tag`, `base`, `origin`…) are there to word when a screen shows them.
- **Steps** (`create/utils/steps.ts`, `create/hooks/use-wizard.ts`): a Record from each question to its step (`createSteps`, `checkoutSteps`), `stepsBy(form, of)` keeping only the fields it names; a field no question of the screen answers (a flag) is left out. `useWizard` holds the steps, Next, Back, Remember and the request, for both wizards. A skipped field is said at the foot of its step (`NotAsked`) unless its reason means nothing here; a step that asks nothing is passed. Next goes by the steps of the core's answer to the typing, not the last answer before it.
- **Confirm**: built from the dry run's plan (one `BranchPlan` per branch), never from its recap, which is the command line's. Apply is held to the plan's fingerprint.
- **A pull request** (`create/components/checkout-*.tsx`, `pr-picker.tsx`, `create/utils/checkout-words.ts`): `Pull request` on step 1 opens checkout's form (`checkoutFormQuery`, out of `['repo', id]`: an event never asks GitHub again, and a refusal is not retried). `checkout.github_unavailable` comes back as an `HttpError` carrying its refusal, whose `params.reason` (`gh_missing`, `signed_out`, `not_on_github`, set by the core's one `worktree.UnavailableParams`, as on every `<command>.prs_unavailable` warning) picks the shared `GitHubAlert`'s words (`utils/github.ts`). The picker answers `pr`, `mine` and `review` itself (`form.setFieldValue`, then a check, since no field of theirs is mounted); a row whose option carries a `problem` is disabled from the start. A number no listed pull request is, once typing pauses, is looked up (`pullRequestQuery`: `pr` with `no_fetch`, outside the form) and shown, chosen only by a click or Enter. The first ask of the form naming a pull request fetches its branch; the form's later asks add `no_fetch` once that ask came back without a refusal of `pr`. The dry run (`reviewQuery`, once per opening and answers) and the run never send it: they fetch, so a stale ref never reaches the plan and `checkout.fetch_failed` shows on Confirm. A failed ask is `useCommandForm`'s `failure`, shown above the picker (GitHub's words for `checkout.github_unavailable`, a red Alert otherwise). Each opening starts on New branch. Its run is `useRun(repo, 'checkout')`, in Create's dialog, through Create's `ProgressView`.
- **Run and done**: the dialog keeps a fixed height while it runs; then a run that went well folds its steps into a summary and lists each worktree with its path (copyable) and next command; a failed or cancelled one keeps its timeline open.
