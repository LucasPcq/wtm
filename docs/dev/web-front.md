# The web front

`wtm-next ui` serves a page that drives wtm from the browser: the web front, a React app in `next/web/`, built by Vite into `next/internal/web/dist/` and embedded in the binary (`go:embed`, `next/internal/web/front.go`). It speaks to the core through the server's API only (`next/README.md`, "The web server"): it reads, asks and runs commands of the catalogue, and it decides nothing the core decides.

## The stack

| Concern | Tool |
| -- | -- |
| Build and dev server | Vite, React, TypeScript 7 (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`); Node pinned in `next/web/.nvmrc` |
| Components and styles | shadcn/ui (`radix-nova`, neutral base, lucide icons) on Tailwind v4, added only through the shadcn CLI or MCP (`npx shadcn@latest add <name>`) so that `src/components/ui/` stays upstream's code |
| Routing | TanStack Router, file-based (`src/routes/`, `routeTree.gen.ts` generated by `tsr generate` before the type check): a repository's screens live under `/r/$repo/…`, `$repo` being the id the server gives it (`web.RepoID`) |
| Server state | TanStack Query: every read, mutation and stream goes through its cache (`src/api/queries/`) |
| Forms | TanStack Form over the form a command's questions return (`src/components/command-form/`) |
| Drag and drop | `@dnd-kit/react`, its pointer and keyboard sensors (the Tree's change of parent) |
| Toasts | `sonner`'s `Toaster`, mounted by the shell (shadcn's wrapper does not type-check under `exactOptionalPropertyTypes`) |
| Types | generated from `next/internal/api/api.v2.schema.json` by json-schema-to-typescript into `src/api/types.gen.ts` (`npm run types`, run before `dev` and `build`): the catalogue's shapes, the names of its commands (`ApiCommandName`) and the server's own (`WebRepo`, `WebVersion`, `WebCall`, `WebRefusal`…); the front types nothing by hand |
| Event stream | `eventsource-parser` (`EventSourceParserStream`) inside TanStack Query's `streamedQuery` |
| Lint, format and tests | oxlint with the rules below and `prettier --check` (part of `npm run build`, a warning or an unformatted file fails it; `npm run format` writes), `tsc -b`, Vitest over `src/**/*.test.{ts,tsx}` (`npm test`, happy-dom), Testing Library and `user-event` for the components, msw for the server (see Tests below) |

## Where code goes

```
src/
  api/                  the server: fetch.ts (the token header, json), token.ts, types.gen.ts, and queries/<resource>.ts,
                        one file per resource the server answers (version, repos, commands, events), its queryOptions
  components/ui/        shadcn/ui, upstream's code: added by the CLI, never edited
  hooks/                shadcn's hooks (use-mobile, for the sidebar), upstream's code too
  components/           what two features share: the page header, the state pages, the logo, the command form
                        (command-form/: a field per kind, the form hook, the answers and the core's problems)
  features/<feature>/   one area of the app: its components, its hooks, the queries only it reads
                        (shell/: the frame, the sidebar, the gates; worktrees/: the Worktrees screen, in
                        list/, detail/, tree/, create/, shared/ (what two of them draw) and hooks/)
  routes/               TanStack's file routes, thin: a route declares its path and renders its feature
  lib/                  pure helpers, no React, no fetch
```

- **A feature owns its area**: a screen or a frame is a folder of `features/`, everything it alone uses inside it. Code moves to `components/` (UI) or `lib/` (no UI) on the second feature that needs it, not before. `components/command-form` is there ahead of its second user: every screen that runs a command asks its questions with it.
- **A route is a path and a feature.** It reads its params and renders the feature's component; no query, no markup of its own.
- **Server state is `api/`'s.** A component reads with `useQuery(xQuery)` and writes with `useMutation` over `api/queries/` (or its feature's queries), never `fetch` itself.
- **A closed set of looks is a type.** A component takes the state (`Connection`, a union) and derives its classes (`cva` variants, a `Record` over the union), never a free class string.
- **A file is named after what it declares**, kebab-case (`connection-footer.tsx` declares `ConnectionFooter`); a hook's file starts with `use-`, in a `hooks/` folder of its own, so that a folder does not mix components and hooks.
- **The address holds what is linkable**: the Worktrees screen's view, filter, search and open worktree are search params of its route (`features/worktrees/search.ts`), never local state.

### The rules the linter keeps

`.oxlintrc.json` runs oxlint's React and TypeScript rules, the bare `fetch`/`EventSource`/`XMLHttpRequest`/`WebSocket` refused outside `src/api/` (`no-restricted-globals`), and the web's own plugin, `lint/wtm.js`, for what built-in rules cannot say. It resolves every import, `@/` and relative alike, to the layer it lands in, and holds each layer to an allowlist (`wtm(layers)`): `src/api/` imports nothing of the app; `lib/` nothing of the app and no package but `cn`, `clsx` and `tailwind-merge`; a route only the router (and `@tanstack/react-query`'s types) and features; `components/` no feature nor route; a feature no other feature nor route, at any depth; `eventsource-parser` only in `src/api/`; `vitest`, `msw` and Testing Library only in tests. A test reaches what its file reaches, and the test kit (`src/test/`). It refuses an effect by any spelling, named, through a namespace or a default import (`wtm(effects)`); the network reached through `window`, `globalThis` or `self`, and `navigator.sendBeacon`, outside `src/api/` (`wtm(network)`); in a test, `renderHook`, `vi.spyOn` on a module of the app, and `vi.mock`/`vi.doMock` in a component test or the test kit (`wtm(test-doubles)`). `lint/fixtures/` plants a violation of each, its first line naming the rule that must refuse it, and `lint/rules.test.ts` (part of `npm test`) checks each is refused, by that rule only. `src/components/ui/` and `src/hooks/` are shadcn's code, out of the lint. A drift found in review becomes a rule there, with its fixture. `make lint-ui` runs the types, the lint and the format check alone. How a change is made here: the `web-front` skill (`.claude/skills/web-front/`).

## The look

The visual spec is the Pencil file `wtm-ui.pen` (the `pencil` MCP; open in the Pen app). It holds shadcn's default kit and wtm's own components built on it: `wtm/Logo`, `wtm/Sidebar` (with its `wtm/Sidebar Footer`), `wtm/Page Header`, `wtm/Empty State`, and one frame per screen and state. The code follows it: a screen is drawn in Pencil first, from these components, validated by the owner, then built; a deviation found while coding goes back into Pencil in the same change.

The identity is shadcn's defaults plus two marks of `docs/dev/identity.md`: the logo (the mark's SVG, its lanes in their light and dark values, the wordmark in Inter 700) and `signature` as `--primary` (`#A6391A` light, `#E8734A` dark, its text white in light and `#17142A` in dark, for contrast). The font is Inter. The theme follows the system's (`prefers-color-scheme`, the `.dark` class set before the first paint in `index.html`), with no toggle.

## How it talks to the server

- **The token.** `wtm-next ui` opens `http://127.0.0.1:<port>/#repo=<id>&token=<token>`. The page reads the fragment once (`src/api/token.ts`), keeps the token in `localStorage` and drops the fragment from the address. Every tab of the origin shares it: a restarted server has a new token, and the tab `wtm-next ui` then opens writes it, which the `storage` event hands to the tabs already open. Every request carries it in `X-Wtm-Token`, never in a query string. A page with no token shows how to open it. A token change reloads the page, so that a restarted server of another version serves its own code; a change of the fragment (an address pasted into the tab) reloads it too, so that its token is read and leaves the address bar.
- **The API layer** (`src/api/`) is the generated types, `fetch.ts` (`request`, fetch with the token header; `json`, its body or the server's error as an `HttpError`), and `queryOptions` per resource (`queries/`). Nothing sits between a component and Query.
- **Reads.** A read of the catalogue (`list`, `tree`, `status`) is `readQuery(repo, command, answers)`, its envelope cached under `['repo', id, …]` and its items' detail typed by the command (`Read<'list'>`), narrowed once there. The front never polls.
- **A worktree's condition and actions are the core's.** Each read, live or GitHub's, publishes a worktree's `condition` (`worktree.Condition`, a closed enum ranked in Go: no worktree, unreadable, missing, rebasing, merged, changed, clean) and its `actions`, already ordered; the screen maps a condition to its look (`conditionLook`) and shows the first action. Over the two reads of one worktree it keeps one rule, `overlaid` (`features/worktrees/shared/condition.ts`), shared by the list and the tree and tested there: a pull request GitHub says is merged wins over changed and clean, with that read's actions; anything else is the live read's.
- **GitHub on demand.** A read asking GitHub (`with_prs`) is `githubQuery`, cached under `['github', id, …]`, which no event of the stream and no reconnect invalidates. Each view asks once, the view on screen only (the list's read in the list, the tree's in the tree), the detail each time it opens; Fetch origin (`fetchOrigin`, a list with `fetch` only) fetches, then the GitHub reads on screen ask again, one per view, and one off screen when it shows again. The list overlays a pull request and whether it merged on the live read, by subject; the tree takes a pull request and the clean action; the detail's header and Review take the pull request from the detail's own GitHub read. GitHub is never asked on an event nor by a timer.
- **Follow-ups.** A follow-up the catalogue cannot run (clean, sync, go, run …) shows as its command line to copy (`commandLineQuery`, `POST /api/command-line`), one the command line cannot spell as its message; never as a button that runs nothing.
- **An operation.** `runStreamed` (`src/api/queries/operations.ts`) posts a command with `Accept: text/event-stream`, hands each event to the caller, the operation's id as soon as the server makes it, and ends with the envelope; `cancel` is `DELETE …/operations/{id}` (`?force=true` the second time). Create's progress lives in Query's cache (`['progress', id, 'create']`), so the dialog shows it again when it opens again, and the list marks the rows it works on.
- **The event stream.** `eventsQuery` (`src/api/queries/events.ts`) is a `streamedQuery` over `GET /api/events`, read with `fetch` (`EventSource` cannot send the header) and parsed by `EventSourceParserStream`. Each line invalidates what it changed: an event of a repository `['repo', id]`, `repo.added` and `repo.removed` the list of repositories; back after a break, everything is read again, the lines in between being lost. Query reconnects it: `refetchInterval` asks again every 2 s once the stream ended or failed, and stops when the server refuses the token, until a token change reloads the page. `connectionOf` reads the query's state as live, reconnecting, connecting or disconnected, which the sidebar's footer shows with the stream's warnings (the bus lost, a repository skipped).
- **Components** hold no `useEffect`: state is derived while rendering, data and side effects go through Query, Router and Form, an outside store through `useSyncExternalStore` (the token). The only effects are in shadcn's own code (`src/components/ui/sidebar.tsx`, its keyboard shortcut; `src/hooks/use-mobile.ts`).
- **Forms.** `useCommandForm` builds a form from a command's `domain.Form` (`POST …/questions`), one value per field keyed by its path (escaped: the form library reads `remember[0]` as nested), a text list as its raw text, split when sent, and `CommandFields` draws each field with the input of its kind (select, multi-select, text, text list, confirm as two choices), where its answer came from, and "Always use this answer" for one the core lets remember. Validation is the core's: each change asks the questions again with the answers changed so far, its problems land under their fields, and its answer becomes the form shown (a field it no longer asks, a default that followed another answer). The front re-encodes no rule (required, allowed options, branch names).
- **Create's words** are the front's: the core's labels, helps and option labels are the command line's copy. `create/words.ts` holds an exhaustive `Record` over create's question paths (a label and one sentence saying what the field is for), over the values of each closed select and confirmation (a title and a line; the schema publishes them as an enum for a select the core marks `closed`), and over the published skip codes (`domain.Skip`, a sentence or `null` for a reason that means nothing in a browser), so a question, an option or a reason the core adds fails the build until it has words. An option of no words is data, a branch, and reads as its value. A field shows its label with Remember on the right when it is rememberable, its answer and where it came from (`origin`: from config, from run.toml, remembered; a default says nothing), then its help.
- **Create's steps** are the front's: an exhaustive `Record` from each of create's question paths (`CreateRequest`'s paths, published by the schema) to its step, so a question create adds fails the build until it has one. A field the core skips is listed at the foot of its step as not asked, with its reason, unless that reason holds on the command line alone; a step it asks nothing of is passed. The last step is the dry run's recap, its apply held to its fingerprint; then the run, phase by phase from the plan's `phases` (named by an exhaustive `Record` over the published phase enum).

## Building it

`make ui` is the only writer of `next/internal/web/dist/`: `npm ci`, `npm test`, `npm run build` in `next/web`, which generates the types and the route tree, type-checks, then builds and lints, so that a type error leaves `dist/` as it was and a lint error fails the CI `ui` gate. The build is committed, so that `go install` gives a binary with its interface, under these guards:

- no source maps (`build.sourcemap: false`);
- `next/internal/web/dist/** linguist-generated=true -diff` in `.gitattributes`: a review reads the sources;
- the CI job `ui` rebuilds from the lockfile with the pinned Node and fails when `dist/` differs from the commit (`git diff --exit-code`, no untracked file);
- goreleaser refuses to release a dirty tree; the release does not ship `wtm-next` yet, and the one that does runs the `ui` gate before it;
- a binary built `-tags noui` (`front_noui.go`) embeds no front and serves a page saying so, its API unchanged; `make test-next` and the CI run the server's tests in both builds.

A change to `next/web/` is committed with the `dist/` that `make ui` writes from it.

## Tests

Two kinds, both under Vitest:

- **Logic** (`*.test.ts` beside the code): a non-trivial pure function — the rows and filters, the tree's nodes, the steps and progress of create, a sentence — called with values, its result compared.
- **Components** (`*.test.tsx`): the whole page rendered at an address (`renderApp(path)`, `src/test/render.tsx`) and used as its user does: queries by role, label or text (`findByRole('link', { name: … })`), actions through `user-event`, assertions on what the screen shows or the address holds. Never a hook called directly (`renderHook`), never a module of the app mocked (`vi.mock`, `vi.doMock`, `vi.spyOn` on it): the linter refuses them. `renderApp` is awaited: it loads the route's code-split modules before rendering, so a test's wait measures the screen only.

The server is mocked at the network level by msw (`src/test/server.ts`): one repository and its worktrees, its reads, `create`'s questions, dry run and stream, the spelling of a command line, an event stream that says nothing. A test that needs another answer overrides one route with `server.use(http.get(…))`; a request no handler answers fails the test. A regression found in a browser gets its component test, named after what the user saw (`a row opens its own worktree, not another`).

## Dev mode

`make ui-dev` serves the front from Vite with hot reload and proxies `/api` to the server of `wtm-next ui` (`WTM_API=http://127.0.0.1:<port>` when it does not listen on 4777). The proxy rewrites `Host` and `Origin` to the server's own, which its guard requires. Open Vite's address with the fragment `wtm-next ui --no-open` prints: `http://localhost:5173/#repo=<id>&token=<token>`.

## Adding a screen

1. Draw it in Pencil from the `wtm/` components; get it validated.
2. Add its feature under `src/features/<feature>/` and a thin route under `src/routes/_shell/r/$repo/`; its reads as `queryOptions` (in `src/api/queries/` when another feature reads them too), its actions as commands of the catalogue.
3. Show what the core returns: a count, a state, an anomaly or an available action arrives in the envelope, and the screen draws it.
4. `make ui`, then commit the sources with `dist/`.
