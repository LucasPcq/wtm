# Configuration

How wtm creates a worktree is set once per repository by `wtm init`: where worktrees go, which branch they start from, how `.env` files reach them and which hooks run. A global config holds what is per machine.

```bash
wtm init                       # the wizard: worktree location, base branch, .env provisioning, hooks
wtm config show                # the resolved project config
wtm config edit                # open config.toml in your editor
wtm init --only hooks --yes    # regenerate one section (env, hooks, worktrees)
```

All wtm files live under `<git-common-dir>/wtm/` (`.git/wtm/` for a normal clone), where git never commits anything, so wtm is invisible to teammates and to `git status`: worktree usage stays personal. Each file there is described in [Where wtm keeps its state](state.md). `config.toml` and `run.toml` are TOML, validated at load time: unknown keys are rejected, not silently ignored.

## Project config: `config.toml`

Generated by `wtm init`, per clone, never committed.

```toml
[worktrees]
base_path   = "../.trees"   # where worktrees are created (relative to repo root), see Moving worktrees
base_branch = "main"        # default base for new worktrees

[env]
strategy = "example"        # example | main | parent (see below)

# Each detected value file and its committed template (schema). wtm distinguishes
# templates (.env.example / .dist / .sample / .template / .tmpl, committed) from
# value files (.env, gitignored). .env.local is detected and flagged local but
# stays syncable.
[[env.file]]
target   = ".env"
template = ".env.example"

[[env.file]]
target = ".env.local"
local  = true

[hooks]
on_create = [
  "pnpm install",                                             # string: runs from worktree root
  { cmd = "pnpm install", cwd = "apps/api" },                 # object: runs from a subdir
  { cmd = "pnpm install", cwd = "apps/web", continue_on_error = true },  # non-fatal
]
on_clean = [
  "docker compose down",                                      # runs right before a worktree is removed
]
```

### Hooks

- `on_create` hooks run in the new worktree once it is created and its `.env` files are provisioned; `on_clean` hooks run in the worktree just before `clean` / `prune` removes it, to tear down external resources. A non-zero hook aborts the operation unless the entry sets `continue_on_error`.
- A hook is a `/bin/sh` line, run from the worktree root or from its `cwd`. It interpolates `{{worktree}}` (the worktree's path), `{{branch}}`, `{{root}}` (the main checkout's path) and, for `on_create`, `{{from_branch}}`, each quoted for the spot it lands in, so a path holding a `'` or a `$` arrives as spelled on disk: `cd {{worktree}}`, `cd "{{worktree}}"` and `cd '{{worktree}}'` all work.
- The raw output of the last run of each phase is kept in `.git/wtm/hooks/<phase>-<branch>.log`.

#### The environment a hook gets

A hook inherits the environment of the wtm command that runs it, `WTM_CORRELATION_ID` included. It also gets the worktree's run variables when **both** of these hold:

- `run.toml` declares a job whose `cmd` or `stop` runs `docker compose` (or `docker-compose`);
- the worktree's `meta.json` records its `isolation` (`isolated` or `verbatim`): every worktree wtm creates does, and an older one once adopted with `wtm env <branch> --isolation isolated` (or `verbatim`).

Then the hook gets these variables, replacing any of the same name it inherited:

| Variable | Value for `feat/login` in `acme` |
| --- | --- |
| `WTM_BRANCH` | `feat/login` |
| `WTM_WORKTREE` | `feat-login`, the branch's slug |
| `WTM_PROJECT` | `acme` |
| `WTM_ORDINAL` | `1`, the worktree's number, allocated before the `on_create` hooks run when it has none yet |
| `WTM_PORT_OFFSET` | `10` (`ordinal × port_offset_block`; `0` for a verbatim worktree) |
| `WTM_ISOLATION` | `isolated` or `verbatim` |
| `COMPOSE_PROJECT_NAME` | `acme-feat-login`; absent for a verbatim worktree. When the worktree's own `.env` (in the directory a compose job runs from) sets it, that value wins |
| each declared port | `DB_PORT=5442`: the base port plus the offset, the base itself for a [shared service](shared-services.md). A name declared by two jobs (two apps each with `PORT`) is left out |

So an `on_clean` running `docker compose down` reaches the stack its `up` started, on the `${DB_PORT}` it bound. When either condition fails, the hook runs with the environment it inherited, unchanged, and no worktree number is allocated for it. Jobs get the same variables and more: see [How `wtm run` works](how-run-works.md#the-job-environment).

### The environment of `wtm exec`

```bash
wtm exec --all -- 'echo "$WTM_BRANCH on port offset $WTM_PORT_OFFSET"'
```

`wtm exec` runs its command with [the run variables a hook gets](#the-environment-a-hook-gets), under the same conditions. One difference: a hook keeps the environment it inherited when no run variable applies, while `wtm exec` **always** removes the variables that describe a worktree (`WTM_WORKTREE`, `WTM_BRANCH`, `WTM_ORDINAL`, `WTM_PORT_OFFSET`, `WTM_ISOLATION`, `COMPOSE_PROJECT_NAME`) before adding the target's. A hook runs on the worktree just created from where you stand; an `exec` command runs in worktrees you are not in, and the values your shell carries would point it at your stack instead of theirs. The recipe is in [Run a command across worktrees](recipes.md#run-a-command-across-worktrees).

## Env strategies

| Strategy | Behavior |
|---|---|
| `example` | Copies the file's committed template from the main checkout, renamed to the file: the `template` recorded in `[[env.file]]`, else the first of `<file>.example`, `.dist`, `.sample`, `.template` and `.tmpl` that exists. Warns and skips the file when there is none. |
| `main` | Copies the actual file from the main checkout. |
| `parent` | Copies from the source worktree (`--from`), falling back to `main`. |

The strategy is recorded per worktree; `wtm create --env-from <strategy>` overrides it for one worktree. Later, [`wtm env`](../wtm_env.md) reconciles a worktree's `.env` against its **template** (the committed schema) plus the **same value source**, adding missing keys and (with `--mode refresh`) settling values that drifted. `--from` overrides the source for one run, and the report always shows which source was used.

## Global config

Created by `wtm init`, personal to each developer. It lives under the OS config directory (`~/.config/wtm/config.toml` on Linux, `~/Library/Application Support/wtm/config.toml` on macOS); `wtm run proxy status` prints the resolved path.

```toml
shell = "zsh"          # zsh | bash | fish

[ui]
animations = true      # false disables every wtm ui animation (tab rule, new-row flash)

[proxy]
port = 11080           # where named job URLs are served, on the loopback only
enabled = true         # false sends every URL back to http://localhost:<port>
```

- `ui.animations` defaults to on when absent; `false` turns off every `wtm ui` animation at once, useful over a slow connection.
- `[proxy]` is the local proxy that serves each job under its own name (`http://web.feat-login.acme.localhost:11080`); both keys default to the values above. What it serves, a port it cannot bind and how to drop the `:11080` are in [Named URLs](addressing.md#the-proxys-port). A job started by another job (a root `turbo run dev`) is served under its own name too: see [Runners](jobs-and-profiles.md#runners).

## Moving worktrees

`base_path` decides where new worktrees go. To move the ones that exist, change it with `wtm relocate --to`:

```console
$ wtm relocate --to ../worktrees --dry-run

  base_path: ../acme.trees → ../worktrees

  To apply (1)
  • feat/login → ../worktrees/feat-login

  = Dry run — no changes made.

$ wtm relocate --to ../worktrees --yes

  ✓ Relocation complete  1 applied

  ✓ feat/login → ../worktrees/feat-login

  ✓ config base_path updated to "../worktrees"
```

- Each worktree moves with `git worktree move`, untracked files included (its `.env` files, `node_modules`). Its branch, `meta.json`, ports and named URLs are keyed by the branch, not the path, so they do not change.
- `wtm relocate` without `--to` keeps `base_path` and moves the worktrees that are not under it. It also **adopts** worktrees created with `git worktree add`: they are moved under `base_path` and their parent is recorded so `wtm sync` works (the wizard asks each one's parent; `--yes` records the base branch).
- A dirty or locked worktree is skipped unless `--force`. A worktree whose jobs are running is never moved: `wtm run down <branch>` first. An occupied destination is never overwritten.

## IDE autocomplete + validation

Every TOML file `wtm init` writes starts with a `#:schema ./schemas/...json` directive. Pair it with [Even Better TOML](https://marketplace.visualstudio.com/items?itemName=tamasfe.even-better-toml) (or the bundled JetBrains TOML plugin) for autocomplete, hover docs and real-time validation. Schemas ship with the binary and are written beside each file every time wtm writes it (`init`, `init --only`, `run init`, `run job` / `run profile`, `relocate`…), no internet required. To refresh them after upgrading without touching a config:

```bash
wtm schema dump            # <git-common-dir>/wtm/schemas/{run,project}.schema.json
wtm schema dump --global   # global.schema.json, beside the global config
```

The schemas of the latest release are also published at `https://wtm.sh/schemas/<name>.json` (`project.schema.json`, `run.schema.json`, `global.schema.json`, `events.v1.json`), for a file written outside a repository or a tool that should not depend on a local copy.
